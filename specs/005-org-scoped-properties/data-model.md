# Phase 1 데이터 모델: 본부·부서 속성과 조직 기반 선택지 좁히기

**Feature**: `005-org-scoped-properties` | **Date**: 2026-08-08

이 기능은 새 저장 구조를 만들지 않는다. 카드 속성값의 형식 하나와, 화면이
계산하는 파생 집합 넷이 전부다. 조직 마스터는 메인 서버 소유이며 읽기만 한다.

---

## 1. 카드 속성값

### 1.1 저장 형식

본부·부서 속성값은 기존 카드 속성 저장소(`Block.Fields["properties"]`)에 들어가며,
`multiSelect`·`multiPerson`과 같은 **문자열 배열**이다.

```
properties: {
  "<본부 속성 ID>": ["<OrgUnit ID>", "<OrgUnit ID>"],
  "<부서 속성 ID>": ["<OrgUnit ID>"]
}
```

값은 조직 단위의 ID다. 이름은 저장하지 않는다 — 조직 관리에서 이름이 바뀌면
카드가 따라가야 한다.

**새 마이그레이션이 없다.** 속성값은 이미 자유 형식 JSON이므로 스키마 변경이
필요하지 않다 (constitution VII의 마이그레이션 규율 대상 아님).

### 1.2 속성 템플릿

| 필드 | 값 |
|---|---|
| `type` | `orgDivision` 또는 `orgDepartment` |
| `options` | **항상 빈 배열**. 선택지는 보드가 아니라 조직 마스터에 있다 |

`options`가 비어 있다는 점이 spec 002와의 경계를 만든다. 카드 접근 규칙은
`options.length > 0`인 속성만 고를 수 있어 이 타입들은 자동으로 제외된다
(spec Assumptions).

### 1.3 검증

서버는 값이 실재하는 조직 ID인지, 카드의 본부 범위 안인지 **검증하지 않는다.**
좁히기는 입력 편의이지 접근 통제가 아니다(spec Assumptions). 검증을 넣으면
조직이 폐지될 때 기존 카드의 저장이 막힌다.

---

## 2. 조직 마스터 (읽기 전용)

이미 있는 모델을 그대로 쓴다. 이 기능은 아무것도 추가하지 않는다.

### 2.1 OrgUnit

| 필드 | 뜻 |
|---|---|
| `id` | 조직 단위 ID. 카드 속성값이 가리키는 대상 |
| `name` | 표시 이름 |
| `type` | `division`(본부) 또는 `department`(부서) |
| `parentId` | 부서의 상위 본부. 본부는 비어 있다 |
| `active` | 비활성 조직은 선택지에서 제외한다 |

계층은 본부-부서 2단계다. 부서의 상위는 항상 본부다(spec Assumptions).

### 2.2 UserOrgProfile

| 필드 | 뜻 |
|---|---|
| `userId` | 사용자 |
| `orgUnitId` | 그 사용자가 속한 조직 단위. 본부일 수도 부서일 수도 있다 |

이 기능이 쓰는 것은 이 두 필드뿐이다. 직책(`primaryDutyId`)·직위·유효기간은
쓰지 않는다.

**소속이 부서인 사용자는 그 부서의 상위 본부에도 속한 것으로 본다.** 조직
관리의 실제 데이터가 그렇다 — 팀장·팀원은 부서에, 본부장은 본부에 배정돼 있다.

## 3. 파생 집합 (화면이 계산)

전부 순수 함수다. 입력은 카드·보드·조직 마스터·소속 목록이고 출력은 ID 집합이다.
서버 왕복이 없다(research R1).

### 3.1 선택된 본부 / 선택된 부서

```
선택된_본부(card, board) = board의 모든 orgDivision 속성에 대해
                            card.properties[속성ID] 를 모아 합집합
선택된_부서(card, board) = 같은 방식으로 orgDepartment 속성에 대해
```

값이 여럿이어도, 속성이 여럿이어도 합집합이다 (FR-009, FR-010).

### 3.2 허용 부서

```
허용_부서(선택된_본부, orgUnits)
    선택된_본부 가 비었으면  →  active 인 department 전체            (FR-008)
    아니면                  →  parentId 가 선택된_본부 에 속한 department  (FR-007)
```

### 3.3 허용 사용자

```
허용_사용자(선택된_본부, 선택된_부서, orgUnits, profiles)
    선택된_부서 가 있으면    →  orgUnitId ∈ 선택된_부서            (FR-011)
    아니면 선택된_본부 이 있으면 →  orgUnitId ∈ 선택된_본부 ∪ 그 하위 부서  (FR-012)
    둘 다 없으면            →  제한 없음 (null 을 돌려 "좁히지 않음"을 표시)  (FR-013)
```

소속이 없는 사용자는 어느 집합에도 들지 않으므로 자연히 빠진다 (FR-014).

`null`과 빈 집합을 구별하는 것이 중요하다. 빈 집합은 "아무도 해당 없음"이고
`null`은 "좁히지 않음"이다.

### 3.4 목록에 실제로 보이는 값

```
표시_목록(허용_집합, 카드에_이미_있는_값)
    허용_집합 이 null 이면  →  전체
    아니면                →  허용_집합 ∪ 카드에_이미_있는_값       (FR-015)
```

**이 합집합이 규칙 하나로 세 가지를 덮는다** — 조직이 없는 사용자, 조직이 바뀐
담당자, 폐지된 조직. 셋 다 "이미 카드에 있으면 남는다"로 같게 처리된다.

## 4. 상태 전이 — 본부가 바뀔 때

본부 속성값이 바뀌면 같은 카드의 부서 속성을 훑는다.

```
본부 변경 시:
  새_허용_부서 = 허용_부서(새_선택된_본부, orgUnits)
  각 orgDepartment 속성에 대해:
      남길 값 = 현재 값 ∩ 새_허용_부서
```

- 부서만 정리한다. 사람 값은 건드리지 않는다 (FR-018)
- 본부 변경과 부서 정리를 **하나의 변경으로** 보낸다 (FR-017). 나눠 보내면 중간
  상태가 저장되고 되돌리기가 두 단계가 된다

---

## 5. 무효 참조

조직 관리에서 사라졌거나 비활성인 ID가 카드에 남을 수 있다.

| 상황 | 처리 |
|---|---|
| 값이 조직 마스터에 없다 | 지우지 않는다. 화면에 문제 있는 값으로 표시한다 (FR-006) |
| 선택지 | 새로 고를 수는 없다 (active만 제공) |
| 이미 있는 값 | 3.4에 따라 목록에 남는다 |

spec 002의 FR-036과 같은 처리다 — 마스터가 메인 서버 소유라 이 플러그인이 정리를
결정할 위치에 있지 않다.
