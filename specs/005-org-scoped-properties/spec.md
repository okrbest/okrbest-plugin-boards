# Feature Specification: 본부·부서 속성과 조직 기반 선택지 좁히기

**Feature Branch**: `005-org-scoped-properties`

**Created**: 2026-08-08

**Status**: Draft

**Input**: User description: "속성 종류에 사람, 다중 사용자처럼 본부, 부서 추가 - 다중선택. 본부 속성을 추가하고 선택한 값이 있으면 부서 목록에는 해당 본부에 속한 부서 리스트만 나오게. 본부 속성 필드가 2개 이상이면 해당 본부들의 모든 팀이 나와야 함. 본부, 부서에 값이 있으면 사용자, 다중 사용자 속성값 리스트에는 해당 본부, 부서 소속 사용자만 나오게"

조직이 얽힌 보드에서는 카드마다 담당 본부와 부서를 적고 그에 맞는 담당자를
고른다. 지금은 본부·부서를 적을 속성 종류가 없어 자유 텍스트나 임의의 선택
목록으로 흉내 내고 있고, 담당자 목록에는 보드 사용자 전체가 그대로 나온다.
65명 중에서 생산팀 사람을 찾아 고르는 일이 카드마다 반복된다.

이 기능은 조직을 카드의 1급 속성으로 만들고, 한 번 적은 조직 값이 그다음
선택지를 좁히게 한다.

설계 배경과 결정 근거는 brainstorming 대화에 있다(임시 산출물, 추적 대상
아님).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 카드에 본부와 부서를 적는다 (Priority: P1)

기획자가 OKR 카드를 만들면서 어느 본부·부서가 맡는지 적는다. 지금은 그럴
속성 종류가 없어 선택 목록을 손으로 만들어 쓰는데, 조직이 바뀌면 보드마다
목록을 고쳐야 하고 보드끼리 이름이 어긋난다.

이 이야기는 조직 관리에 등록된 본부·부서를 그대로 고르게 만든다.

**Why this priority**: 이 기능의 존재 이유다. 나머지 이야기는 모두 카드에
조직 값이 적혀 있다는 전제 위에 선다.

**Independent Test**: 보드에 본부 속성과 부서 속성을 추가하고, 카드를 열어
값을 고른 뒤 표와 보드 보기에서 이름이 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 속성 추가 메뉴, **When** 사용자가 속성 종류를 고르면, **Then** 목록에 본부와 부서가 있다
2. **Given** 본부 속성이 있는 카드, **When** 값을 고르면, **Then** 조직 관리에 등록된 활성 본부만 선택지로 나온다
3. **Given** 본부 속성, **When** 값을 여러 개 고르면, **Then** 모두 저장되고 함께 표시된다
4. **Given** 값이 저장된 카드, **When** 표·보드 보기에서 그 카드를 보면, **Then** 조직 ID가 아니라 조직 이름이 보인다
5. **Given** 조직 관리에서 폐지된 조직이 값으로 남은 카드, **When** 그 카드를 보면, **Then** 값이 사라지지 않고 문제 있는 값임이 표시된다

---

### User Story 2 - 본부를 고르면 부서 목록이 좁혀진다 (Priority: P2)

부서는 25개가 넘는다. 담당 본부를 이미 적었는데도 전체 목록에서 찾아야 하면
잘못 고르기 쉽고, 잘못 고른 것은 나중에 알아채기 어렵다.

이 이야기는 이미 적은 본부를 근거로 부서 선택지를 줄인다.

**Why this priority**: P1이 만든 값을 처음으로 활용한다. 이것 없이도 P1은
성립하지만, 있으면 입력 오류가 눈에 띄게 줄어든다.

**Independent Test**: 본부를 생산으로 고른 카드에서 부서 선택지를 열어 생산본부
소속 부서만 나오는지 확인하고, 본부를 비운 뒤 전체가 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 본부=생산인 카드, **When** 부서 선택지를 열면, **Then** 생산본부에 속한 부서만 나온다
2. **Given** 본부 값이 비어 있는 카드, **When** 부서 선택지를 열면, **Then** 전체 활성 부서가 나온다
3. **Given** 본부=생산·관리인 카드, **When** 부서 선택지를 열면, **Then** 두 본부의 부서가 모두 나온다
4. **Given** 본부 속성이 두 개인 보드에서 각각 생산·연구가 적힌 카드, **When** 부서 선택지를 열면, **Then** 두 본부의 부서가 모두 나온다
5. **Given** 본부=관리·부서=재경전산팀인 카드, **When** 본부를 생산으로 바꾸면, **Then** 부서 값이 비워진다
6. **Given** 같은 상태, **When** 본부를 생산으로 바꾸면, **Then** 그 변경이 한 번의 되돌리기로 되돌아간다

---

### User Story 3 - 조직에 맞는 담당자만 고른다 (Priority: P3)

담당자 목록에 팀 전체가 나오면, 카드의 담당 조직과 무관한 사람을 고르는 일이
생긴다. 조직을 이미 적었다면 그 안에서 고르는 것이 자연스럽다.

이 이야기는 카드의 조직 값으로 사람 선택지를 좁힌다.

**Why this priority**: P1·P2가 만든 값을 사람 선택에 연결한다. 없어도 조직
입력은 완성되지만, 있으면 이 기능이 실제로 시간을 줄여준다.

**Independent Test**: 본부·부서가 적힌 카드에서 담당자 선택지를 열어 그 소속만
나오는지 확인하고, 조직 값을 비운 뒤 전체가 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 본부=생산이고 부서가 빈 카드, **When** 담당자 선택지를 열면, **Then** 생산본부와 그 하위 부서 소속만 나온다
2. **Given** 본부=생산·부서=생산팀인 카드, **When** 담당자 선택지를 열면, **Then** 생산팀 소속만 나온다
3. **Given** 본부·부서가 모두 빈 카드, **When** 담당자 선택지를 열면, **Then** 좁히지 않은 전체 목록이 나온다
4. **Given** 조직 정보가 등록되지 않은 사용자, **When** 조직 값이 있는 카드에서 담당자 선택지를 열면, **Then** 그 사용자는 선택지에 없다
5. **Given** 이미 담당자로 지정된 사용자가 카드의 조직 범위 밖인 카드, **When** 담당자 선택지를 열면, **Then** 그 사용자는 목록에 남아 있다
6. **Given** 본부=관리·담당자=재경전산팀원인 카드, **When** 본부를 생산으로 바꾸면, **Then** 담당자는 그대로 유지된다

---

### User Story 4 - 조직으로 거르고 묶고 내보낸다 (Priority: P4)

조직 값을 적어 두면 그것으로 뷰를 거르고 묶어 보고 싶어진다. 내보낸 파일에
조직 ID가 찍혀 나오면 읽을 수 없다.

**Why this priority**: 운영 편의다. 없어도 입력과 좁히기는 온전히 동작한다.

**Independent Test**: 본부 속성으로 필터를 걸고, Group by를 본부로 바꾸고,
CSV를 내려받아 이름이 찍혔는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 본부 속성이 있는 보드, **When** 필터에서 그 속성을 고르면, **Then** 조직 관리에 등록된 본부가 선택지로 나온다
2. **Given** 본부=생산 필터, **When** 뷰를 보면, **Then** 그 값을 가진 카드만 남는다
3. **Given** 본부 속성으로 Group by한 뷰, **When** 뷰를 보면, **Then** 본부별로 묶여 보인다
4. **Given** 값이 여러 개인 카드, **When** Group by한 뷰를 보면, **Then** 그 카드가 해당하는 그룹마다 나타난다
5. **Given** 조직 값이 있는 보드, **When** CSV로 내보내면, **Then** 조직 ID가 아니라 이름이 찍힌다

---

### Edge Cases

- 조직 관리에서 부서가 폐지되면? → 카드에 남은 값은 지우지 않고 문제 있는 값으로 표시한다.
- 본부를 바꿔 부서가 비워졌는데 되돌리면? → 본부와 부서가 함께 원래대로 돌아간다.
- 본부에 부서가 하나도 없으면? → 부서 선택지가 빈 목록이 된다. 이미 적힌 값은 남는다.
- 서로 다른 본부와 부서를 섞어 고르면(본부=생산, 부서=총무팀)? → 부서 기준을 따르므로 총무팀 소속만 담당자로 나온다.
- 조직 정보가 없는 사용자가 이미 담당자인 카드에서 조직 값을 새로 적으면? → 그 담당자는 목록에 남는다.
- 사용자의 소속이 나중에 바뀌면? → 다음에 선택지를 열 때 새 소속으로 판정된다. 이미 적힌 담당자는 바뀌지 않는다.
- 보드에 부서 속성만 있고 본부 속성이 없으면? → 부서 선택지는 전체가 나오고, 담당자는 적힌 부서 기준으로 좁혀진다.

## Requirements *(mandatory)*

### Functional Requirements

**속성 종류**

- **FR-001**: 속성 종류 목록에 본부와 부서를 제공해야 한다
- **FR-002**: 두 속성 모두 값을 여러 개 가질 수 있어야 한다
- **FR-003**: 선택지는 보드가 아니라 조직 관리에 등록된 활성 조직에서 와야 한다
- **FR-004**: 본부 속성의 선택지는 본부로, 부서 속성의 선택지는 부서로 한정해야 한다
- **FR-005**: 저장된 값은 화면에서 조직 이름으로 표시해야 한다
- **FR-006**: 조직 관리에 더 이상 없는 값은 지우지 않고 문제 있는 값임을 화면에 표시해야 한다

**부서 좁히기**

- **FR-007**: 카드에 본부 값이 하나라도 있으면 부서 선택지를 그 본부들에 속한 부서로 한정해야 한다
- **FR-008**: 카드에 본부 값이 전혀 없으면 부서 선택지에 전체 활성 부서를 제공해야 한다
- **FR-009**: 한 본부 속성에 값이 여럿이면 그 값들의 부서를 합쳐서 제공해야 한다
- **FR-010**: 보드에 본부 속성이 둘 이상이면 모든 본부 속성의 값을 합쳐서 판정해야 한다

**사람 좁히기**

- **FR-011**: 카드에 부서 값이 있으면 사람·다중사용자 속성의 선택지를 그 부서들 소속 사용자로 한정해야 한다
- **FR-012**: 카드에 부서 값이 없고 본부 값만 있으면 그 본부들과 그 하위 부서 소속 사용자로 한정해야 한다
- **FR-013**: 카드에 본부·부서 값이 모두 없으면 사람 선택지를 좁히지 않아야 한다
- **FR-014**: 조직 정보가 등록되지 않은 사용자는 좁힘이 적용될 때 선택지에서 제외해야 한다
- **FR-015**: 좁힘이 적용되는 모든 속성에서, 그 카드에 이미 저장된 값은 범위를 벗어나도 목록에 유지해야 한다

**값 정합성**

- **FR-016**: 본부 값이 바뀌어 부서 값이 범위를 벗어나면 그 부서 값을 자동으로 비워야 한다
- **FR-017**: 본부 값 변경과 그에 따른 부서 값 정리는 한 번의 되돌리기로 함께 되돌아가야 한다
- **FR-018**: 본부·부서 값이 바뀌어도 이미 지정된 사람 값은 바꾸지 않아야 한다

**뷰 기능**

- **FR-019**: 두 속성으로 뷰를 거를 수 있어야 하며, 필터 선택지도 조직 관리에서 와야 한다
- **FR-020**: 두 속성으로 뷰를 묶을 수 있어야 한다
- **FR-021**: 내보내기 결과물에 조직 이름이 나와야 한다

**적용 범위**

- **FR-022**: 좁힘은 사람·다중사용자 속성이 나타나는 모든 화면에서 같게 동작해야 한다
- **FR-023**: 본부·부서 속성이 없는 보드의 동작은 이 기능 도입 전과 같아야 한다

### Key Entities

- **본부 속성값**: 카드가 가리키는 본부 목록. 조직 관리의 본부를 가리키며 여러 개일 수 있다.
- **부서 속성값**: 카드가 가리키는 부서 목록. 조직 관리의 부서를 가리키며 여러 개일 수 있다.
- **조직 단위(Org Unit)**: 본부와 부서. 부서는 본부에 속한다. 이 기능은 조회만 하고 관리하지 않는다.
- **사용자 소속**: 어떤 사용자가 어느 조직 단위에 속하는지. 사람 선택지를 좁히는 근거이며, 이 기능은 조회만 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 본부를 지정한 카드에서 부서 선택지에 다른 본부의 부서가 나오지 않는다 (오출 0건)
- **SC-002**: 조직을 지정한 카드에서 담당자 선택지에 그 범위 밖 사용자가 새로 나오지 않는다 (이미 지정된 값 제외, 오출 0건)
- **SC-003**: 담당자를 고를 때 훑어야 하는 후보 수가 조직 지정 전 대비 줄어든다 (생산본부 기준 65명 → 20명 이하)
- **SC-004**: 본부를 바꿔 부서가 비워진 뒤 되돌리기 한 번으로 두 값이 함께 복원된다 (100%)
- **SC-005**: 조직 관리에서 조직이 폐지돼도 그 값을 가진 카드에서 값이 사라지지 않는다 (데이터 손실 0건)
- **SC-006**: 본부·부서 속성을 쓰지 않는 보드에서 카드 조회·편집 동작과 응답 시간이 이 기능 도입 전과 같다 (동작 변화 0건)
- **SC-007**: 보드 관리자가 본부 속성을 추가하고 카드에 값을 넣기까지 2분 이내에 마칠 수 있다

## Assumptions

- 본부·부서 마스터와 사용자별 소속은 이 플러그인 밖(메인 서버의 조직 관리 기능)에서 관리된다. 이 기능은 읽기만 하며 등록·수정 화면을 제공하지 않는다.
- 조직 계층은 현재 본부-부서 2단계다. 부서의 상위는 항상 본부다.
- 사용자는 조직 단위 하나에 속한다. 겸직은 다루지 않는다.
- 선택지 좁히기는 **입력 편의이지 접근 통제가 아니다.** 서버는 저장 시점에 값이 범위 안인지 검증하지 않으며, 화면을 거치지 않은 요청으로는 범위 밖 값을 넣을 수 있다. 카드 단위 접근 통제는 `specs/002-card-property-access/`가 담당한다.
- 속성 기준 카드 접근 권한(spec 002)의 규칙 대상에 이 속성들을 넣지 않는다. 규칙은 보드에 값 목록이 정의된 속성만 고를 수 있고, 이 속성들의 선택지는 보드가 아니라 조직 관리에 있다.
- 값이 여러 개인 속성으로 묶으면 한 카드가 여러 그룹에 나타난다. 기존 다중선택·다중사용자 속성의 동작을 그대로 따른다.
- 사용자 소속 정보를 화면에 내려보내는 범위는 그 보드가 이미 사람 선택기에 보여주는 사용자로 한정한다. 보드에서 볼 수 없는 사람의 소속은 내려보내지 않는다.
