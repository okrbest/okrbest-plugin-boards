# 검증 가이드: 직책 속성

**Feature**: `006-org-duty-property` | **Date**: 2026-08-14

구현이 실제로 동작하는지 종단으로 확인하는 절차다. 요구사항 식별자는
[spec.md](./spec.md), 판정 규칙은 [data-model.md](./data-model.md)에 있다.

---

## 사전 준비

**소스만 고쳐서는 반영되지 않는다.** 빌드·배포해야 실행 중인 Mattermost가 바뀐다.

```bash
# watch가 돌고 있으면 저장할 때마다 자동 배포된다 (저장 → 반영 11~14초)
cd webapp && MM_DEBUG=1 npm run debug:watch

# 일회성으로 올리려면
cd webapp && npx webpack --mode=development && cd ..
make deploy-from-watch
```

배포 후 **브라우저 하드 리프레시**가 필요하다. 번들 파일명에 해시가 박혀 있어
자동 새로고침이 없다.

이 기능은 webapp만 바꾸므로 Go 빌드(`make server-linux`)는 필요 없다.

### 검증 데이터

`kkv` 팀의 조직 관리에 등록된 값이다. 직책과 직위가 섞여 있어야 FR-004를 잴 수 있다.

| 종류 | 개수 | 이름 |
|---|---|---|
| 직책 (보여야 함) | 9 | CEO, 고문, 본부장, CFO, CHRO, COO, CSO, 팀장, 팀원 |
| 직위 (보이면 안 됨) | 9 | — |

검증용 보드를 새로 하나 만든다. 기존 OKR 보드에서 하지 않는다 — 실제 데이터를
건드리게 된다.

---

## 1. 속성 추가와 다중 선택 (P1)

FR-001, FR-002, FR-003, FR-005

1. 보드에서 속성을 추가하고 유형 목록을 연다.
   - **확인**: 목록에 **직책**이 있다. 본부·부서 곁에 있다. (FR-001)
2. 직책 속성을 만들고 카드를 연다. 값 자리를 클릭한다.
   - **확인**: 직책 9개가 모두 보인다. (FR-003)
   - **확인**: 순서가 CEO → 고문 → 본부장·CFO·CHRO·COO·CSO → 팀장 → 팀원이다.
     서열 순이지 가나다순이 아니다. (FR-005)
3. **본부장**을 고른다. 목록을 다시 열어 **팀장**도 고른다.
   - **확인**: 라벨 두 개가 나란히 남는다. (FR-002)
   - **확인**: 모양과 색이 본부·부서 라벨과 같다. (FR-012)
4. 라벨 하나의 x를 눌러 지운다.
   - **확인**: 나머지 하나는 그대로다.
5. 표 보기로 나간다.
   - **확인**: 칸에 직책 이름이 보인다. ID가 아니다.

---

## 2. 좁히기가 없다는 확인 (P1)

FR-003 — 안 만든 기능을 확인하는 절이다. 본부·부서에는 좁히기가 있으므로,
직책에 실수로 딸려 들어가지 않았는지 본다.

1. 같은 보드에 본부 속성과 부서 속성도 추가한다.
2. 카드의 본부를 **CFO - 관리**로 고른다.
3. 직책 값 자리를 연다.
   - **확인**: 직책 9개가 그대로 다 보인다. 줄어들지 않았다.
4. 본부를 **COO - 생산**으로 바꾼다.
   - **확인**: 이미 고른 직책 값이 지워지지 않았다. (본부를 바꾸면 부서는 정리되지만
     직책은 아니다)
   - **확인**: 직책 목록은 여전히 9개다.

---

## 3. 직위는 보이지 않는다 (P1)

FR-004

1. 직책 편집기, 필터 패널, 묶기 목록을 차례로 연다.
   - **확인**: 세 곳 모두 직책 9개만 나온다. 직위 9개는 **한 곳에서도** 나오지 않는다.

조직 관리 화면에서 직책과 직위 목록을 나란히 놓고 대조한다.

---

## 4. 필터와 묶기 (P2)

FR-007, FR-008

1. 카드를 여러 장 만들고 직책을 서로 다르게 넣는다. 최소 한 장은 직책을 두 개 넣는다.
2. 필터를 열어 속성으로 **직책**을 고른다.
   - **확인**: 검색창과 체크박스 목록이 나온다. 본부·부서 필터와 화면이 같다.
   - **확인**: 검색창에 `팀`을 치면 팀장·팀원만 남는다.
3. **팀장**을 체크한다.
   - **확인**: 팀장이 든 카드만 남는다.
   - **확인**: 직책을 두 개 가진 카드도, 그중 하나가 팀장이면 남는다. (FR-007)
4. 필터를 끄고 보기 설정에서 **직책으로 묶기**를 고른다.
   - **확인**: 그룹 제목이 **직책 이름**이다. ID가 아니다. (FR-008)
   - **확인**: 값이 없는 카드는 `No <속성 이름>` 그룹에 모인다.
   - **확인**: 값이 둘인 카드의 그룹 제목은 두 이름이 `, `로 이어진다.

ID가 보이면 `centerPanel`의 이름 해석에 직책이 빠진 것이다.

---

## 5. 내보내기 (P3)

FR-009

1. 직책 값이 있는 보기를 CSV로 내보낸다.
2. 파일을 연다.
   - **확인**: 직책 칸에 이름이 있다. 26자 ID가 **하나도** 없다.
   - **확인**: 값이 둘인 카드는 `"본부장|팀장"` 형태다. 본부·부서 칸과 구분자가 같다.

---

## 6. 사라진 직책 (P1)

FR-006 — 이 기능에서 가장 틀리기 쉬운 자리다.

1. 카드에 **고문**을 넣는다.
2. 조직 관리에서 **고문**을 비활성으로 바꾼다.
3. 브라우저를 새로고침하고 그 카드를 연다.
   - **확인**: 값이 **사라지지 않았다**.
   - **확인**: 이름 자리에 `(removed)` 표시와 경고색 라벨이 보인다.
   - **확인**: 선택 목록을 열면 그 값이 목록에 남아 있다 — 지우려면 보여야 한다.
   - **확인**: 새로 고를 수 있는 목록에는 고문이 없다 (활성 8개).
4. 같은 카드를 묶기와 내보내기로 확인한다.
   - **확인**: 둘 다 ID를 그대로 보여준다. "알 수 없음"으로 뭉개지 않는다.
5. 조직 관리에서 고문을 다시 활성으로 되돌린다.
   - **확인**: 새로고침하면 이름이 돌아온다.

## 7. 회귀 확인

005가 만든 동작이 그대로인지 본다. SC-006.

1. 본부를 고르면 부서 목록이 그 본부의 부서로 좁혀진다.
2. 본부를 바꾸면 맞지 않는 부서 값이 정리된다.
3. 본부·부서가 있으면 담당자 후보가 그 조직 사람으로 좁혀진다.
   - **확인**: 카드에 직책을 넣어도 담당자 후보는 **달라지지 않는다**. (FR-010)
4. 공유 대화상자의 접근 규칙을 연다.
   - **확인**: 속성 목록에 직책 속성이 **없다**. 본부·부서도 없다. (FR-011)
   - **확인**: 규칙의 직책 조건(보는 사람의 직책)은 그대로 동작한다.

## 8. 품질 게이트

webapp만 닿으므로 webapp 게이트만 돌린다. Go 파일을 하나도 바꾸지 않았음을 먼저
확인한다(`git diff --stat`).

```bash
make webapp-ci
```

`make webapp-ci`는 기준선에서도 실패한다. **개수가 아니라 실패 목록 diff로 판정한다.**
세 단계를 따로 돌려 대조한다.

```bash
cd webapp
npm run check          # eslint + stylelint
npm run test           # Jest
npm run check-types    # tsc
```

기준선(깨끗한 상태)과 비교해 **새로 생긴 실패가 없어야** 통과다. 기준선은
`main`에서 같은 명령을 돌려 얻는다.
