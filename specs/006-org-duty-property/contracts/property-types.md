# 계약: 직책 속성 타입

**Feature**: `006-org-duty-property`

새 속성 타입 하나가 기존 속성 체계와 맺는 계약이다. 저장 형식은
[data-model.md](../data-model.md) 1절에 있고, 여기서는 **레지스트리와 주변 코드가 이
타입을 어떻게 다루는가**를 정한다.

005의 [본부·부서 계약](../../005-org-scoped-properties/contracts/property-types.md)을
확장한다. 그 문서가 정한 규칙 중 이 문서가 다시 말하지 않는 것은 **직책에도 그대로
적용된다.**

---

## 1. 타입 식별자

```
orgDuty     직책
```

`webapp/src/blocks/board.ts`의 `PropertyTypeEnum` 유니온에 추가한다.

`multiOrgDuty`로 쓰지 않는다. 본부·부서와 같은 이유다 — 처음부터 다중값이고 단일값
짝이 없어서 접두사가 구별하는 것이 없다.

---

## 2. PropertyType 능력

| 능력 | 값 | 근거 |
|---|---|---|
| `isMultiValue` | `true` | 값이 배열 (FR-002) |
| `isPersonLike` | `false` | 값이 사용자 ID가 아니다 |
| `canFilter` | `true` | FR-007 |
| `canGroup` | `true` | FR-008 |
| `filterValueType` | `'orgUnit'` | 3절 |
| `Editor` | 직책 에디터 | 4절 |
| `name` | `'OrgDuty'` | 레지스트리 관례 |

새 능력을 `PropertyType`에 추가하지 않는다. 005가 `isMultiValue`·`isPersonLike`를
도입하면서 이 자리를 이미 만들어 뒀다.

---

## 3. 필터

`filterValueType`은 **새로 만들지 않고** `'orgUnit'`을 쓴다(research R3).

이 키가 정하는 것은 "어떤 필터 UI인가"이고, 직책 필터는 본부·부서 필터와 화면이 같다 —
검색창 하나에 체크박스 목록. 조직 필터 패널이 속성 타입을 보고 선택지 출처만 고른다.

| 속성 타입 | 선택지 출처 |
|---|---|
| `orgDivision` | 팀의 활성 본부 |
| `orgDepartment` | 팀의 활성 부서 전체 (본부로 좁히지 않는다) |
| `orgDuty` | 팀의 활성 직책 전체 |

필터 조건은 `includes` 하나다. 값이 여러 개인 카드는 그중 하나만 걸려도 결과에
포함된다(FR-007).

**패널 이름은 그대로 둔다.** `OrgUnitFilterPanel`이 직책도 다루면 이름이 살짝 어긋나지만,
이름을 바꾸면 005 계약 문서까지 따라 고쳐야 한다. 여기 적어 두는 것으로 갈음한다.

---

## 4. 에디터

본부·부서와 **같은 에디터를 쓴다**(`orgUnitEditor`). 직책 전용 컴포넌트는 목록을
넘기는 껍데기뿐이다.

이를 위해 에디터의 props 타입을 실제 사용 범위로 낮춘다(research R1).

```
// 이전
options: OrgUnit[]      allUnits: OrgUnit[]

// 이후
options: {id, name}[]   allUnits: {id, name}[]
```

에디터가 `OrgUnit`에서 읽는 필드는 `id`·`name`뿐이다. `type`·`parentId`는 쓰지 않는다.
타입을 낮춰도 본부·부서 동작은 그대로다 — **행동 변화 없는 타입 정리**다.

| 항목 | 직책 에디터 |
|---|---|
| 선택지 | `getDuties(teamId)` 전체 |
| 좁히기 | 없다. 카드의 다른 값이 목록을 바꾸지 않는다 (FR-003) |
| 정렬 | 서버 순서 그대로 (research R4) |
| 다중 선택 | `ValueSelector`의 `isMulti` — 본부·부서와 동일 |
| 선택지 생성·수정·삭제 | 불가 (`fixedOptions`) — 마스터는 읽기 전용 |
| 사라진 값 | 목록에 남기고 경고색 + `(removed)` |

---

## 5. 표시와 내보내기

### 화면

라벨 형태로 보여준다. 본부·부서와 색·모양이 같다.

### CSV

`csvExporter`의 조직 타입 집합에 `orgDuty`를 넣는다. `PropertyType.exportValue`는
redux에 닿지 못하는 순수 함수라 ID밖에 모른다 — 사람 속성이 이미 쓰는 예외 경로를
그대로 탄다.

| 상황 | 출력 |
|---|---|
| 값 하나 | `"팀장"` |
| 값 둘 | `"본부장\|팀장"` (구분자 `\|`, 본부·부서와 동일) |
| 사라진 직책 | ID 그대로 |
| 빈 값 | 빈 칸 |

---

## 6. 묶기

`canGroup: true`만으로는 부족하다. 조직 속성은 `options`가 비어 있어서, 일반 다중값
묶기 경로를 타면 화면에 **ID가 그대로 찍힌다.**

`centerPanel`의 그룹 이름 해석기가 조직 속성을 따로 처리하는 이유이고, 여기에 직책을
포함시킨다. 이름 출처는 합친 조회 맵이다([data-model.md](../data-model.md) 3절).

| 그룹 | 이름 |
|---|---|
| 직책 하나 | 직책 이름 |
| 직책 여럿 | 이름을 `, `로 이어 붙인다 |
| 값 없음 | `No <속성 이름>` |
| 사라진 직책 | ID 그대로 |

## 7. i18n

새 문자열은 하나뿐이다.

| ID | en | ko |
|---|---|---|
| `PropertyType.OrgDuty` | `Duty` | `직책` |

필터 검색창 문구(`FilterPanel.search-org-units`)와 사라진 값 표시
(`OrgProperty.unknownUnit`)는 기존 것을 재사용한다. 두 문자열 모두 조직 단위에만
해당하는 말을 쓰지 않으므로 직책에도 맞는다.

원칙 V에 따라 `en.json`과 `ko.json`을 같은 변경에서 갱신한다.

---

## 8. 접근 규칙

**직책 속성은 접근 규칙 대상이 아니다**(FR-011). 코드를 더해서 막는 게 아니라 이미
구조가 막는다 — 규칙 편집기는 선택지 목록을 가진 속성만 고르는데, 조직 속성의 `options`는
항상 비어 있다.

접근 규칙에 이미 있는 "직책" 조건과 헷갈리지 않아야 한다.

| | 무엇을 가리키나 |
|---|---|
| 규칙의 직책 조건 | **보는 사람**의 직책 — 누구에게 권한을 줄지 |
| 직책 속성 (이 기능) | **카드**에 적힌 직책 — 무엇에 관한 카드인지 |

둘은 이름만 같고 서로 참조하지 않는다.

---

## 9. 하위 호환

`orgDuty`를 모르는 구버전 클라이언트는 레지스트리 기본 동작으로 `unknown` 속성으로
떨어뜨린다. 값은 건드리지 않으므로 신버전에서 다시 열면 그대로 보인다. 본부·부서가
005에서 배포될 때와 같은 상황이다.
