# 검증 가이드: OKR Board로 사용

**Feature**: `008-okr-board-mode` | **Date**: 2026-08-14

구현이 실제로 동작하는지 종단으로 확인하는 절차다. 요구사항 식별자는
[spec.md](./spec.md), 판정 규칙은 [data-model.md](./data-model.md)에 있다.

---

## 사전 준비

**이번에는 Go도 고치므로 서버 빌드가 필요하다.** 006·007과 다른 점이다.

```bash
MM_DEBUG=1 make server-linux            # Go 변경 후 필수
cd webapp && npx webpack --mode=development && cd ..
make deploy-from-watch
```

webpack watch만 돌고 있으면 **Go 변경이 반영되지 않는다.** 하위 카드 채움이 서버에
있으므로, 그 절을 검증하기 전에 반드시 `make server-linux`를 거친다.

배포 후 브라우저 하드 리프레시.

### 검증 데이터

검증용 보드를 새로 만든다. FY27 실보드는 7절에서만 **읽기로** 확인한다.

---

## 1. 체크박스 자리와 켜기 (P1)

FR-001, FR-002, FR-003

1. 새 보드를 만들고 공유 대화상자를 연다.
   - **확인**: "카드 접근 권한" 섹션 **위에** "OKR Board로 사용" 스위치가 있다.
   - **확인**: 처음에는 꺼져 있다.
2. 켠다.
   - **확인**: 보드에 `유형` 선택 속성이 생긴다.
   - **확인**: 값이 `Objective`, `Key Results`, `Tasks` 셋이다.
3. 대화상자를 닫았다 다시 연다.
   - **확인**: 스위치가 켜진 채다. (FR-002)
4. 저장 형태를 본다.
   ```bash
   docker exec ... -c "SELECT properties->'okrBoard' FROM focalboard_boards WHERE id='<보드 ID>';"
   # 기대: {"propertyId": "...", "levels": ["...","...","..."]}
   ```
   - **확인**: 값 **이름이 아니라 ID**가 들어 있다.

## 2. 이미 있는 속성을 알아본다 (P1)

FR-002, FR-004, SC-002 — **이 기능에서 가장 조심할 절이다**

1. 새 보드에 `유형` 선택 속성을 손으로 만들고 값 `Object`를 넣는다.
2. 카드 두 장을 만들어 둘 다 `Object`로 지정한다.
3. "OKR Board로 사용"을 켠다.
   - **확인**: `유형` 속성이 **하나뿐이다.** 새로 만들어지지 않았다.
   - **확인**: 값 이름이 `Objective`로 바뀌었다.
   - **확인**: **카드 두 장이 여전히 그 값을 들고 있다.** 비지 않았다.
   - **확인**: `Key Results`, `Tasks`가 뒤에 더해졌다.
4. 이름이 `유형`인 **텍스트** 속성이 있는 보드에서도 켜 본다.
   - **확인**: 그 속성은 그대로 두고 선택 속성을 새로 만든다.

---

## 3. 클라이언트가 만드는 카드 (P2)

FR-006, FR-006a, FR-009, FR-013

1. 켜진 보드에서 카드를 만든다.
   - **확인**: 유형이 `Objective`다.
2. 표·칸반·갤러리·달력·헤더 버튼에서 각각 만든다.
   - **확인**: 다섯 곳 결과가 같다. (SC-005)
3. `유형 = Tasks` 필터를 걸고 카드를 만든다.
   - **확인**: 유형이 `Tasks`다 — 필터가 정한 값을 덮지 않는다. (FR-009)
4. 스위치를 끄고 카드를 만든다.
   - **확인**: 유형이 비어 있다.
   - **확인**: 속성과 기존 카드 값은 그대로다. (FR-011)
5. **템플릿 경로** — 스위치를 다시 켜고 아래를 훑는다. **`addCard`가 기본 템플릿이 걸린
   보기에서 첫 줄에 빠져나가므로, 채움을 거기에만 두면 이 절이 통째로 실패한다.**
   1. 유형 값이 **없는** 카드 템플릿을 하나 만든다 (카드 상세 → New template from card).
   2. 보기의 기본 템플릿으로 지정하고 "+ New"를 누른다.
      - **확인**: 유형이 `Objective`다.
   3. 유형을 `Key Results`로 박은 템플릿을 하나 더 만들고 그것으로 카드를 만든다.
      - **확인**: `Key Results`다. **단계가 템플릿을 덮지 않는다.** (FR-009)
   4. **3단계 카드에서** "New template from card"로 템플릿을 만들고 그것으로 카드를 만든다.
      - **확인**: `Tasks`다. 템플릿이 물려준 깊이를 읽었다는 뜻이다. (FR-006a)
      - 여기서 `Objective`가 나오면 깊이를 0으로 굳혀 놓은 것이다.

## 4. 하위 카드 (P2) — 서버 쪽

FR-007, FR-008. **`make server-linux`를 거쳤는지 먼저 확인한다.**

1. 켜진 보드에서 Objective 카드를 만든다.
2. 표에서 그 카드의 하위 카드를 만든다.
   - **확인**: 유형이 `Key Results`다.
3. 그 밑에 또 만든다.
   - **확인**: `Tasks`다.
4. 또 만든다 (4단계).
   - **확인**: `Tasks`다.
5. 카드 상세의 하위 카드 영역에서도 만든다.
   - **확인**: 표에서 만든 것과 결과가 같다.
6. **부모 속성 상속 확인** — 부모 카드에 본부·부서 값을 넣고 하위 카드를 만든다.
   - **확인**: 본부·부서가 그대로 내려왔다. (FR-008, SC-003)
   - **확인**: 유형만 단계 값으로 바뀌었다.

이 6번이 이 기능에서 가장 깨지기 쉬운 자리다. 클라이언트가 유형을 실어 보내면 서버가
부모 상속을 건너뛴다.

## 5. 강제하지 않는다 (P2)

FR-010, FR-012

1. 자동으로 채워진 3단계 카드의 유형을 `Objective`로 바꾼다.
   - **확인**: 바뀐 채로 남는다. 되돌아가지 않는다.
2. 카드를 닫았다 연다.
   - **확인**: 그대로다.
3. 유형을 비운다.
   - **확인**: 비어 있는 채다.
4. 값 목록에 `검토`를 하나 더 만든다.
   - **확인**: 새 카드는 여전히 단계 값으로 채워진다. (FR-005)
5. `Tasks`를 `할 일`로 이름을 바꾼다.
   - **확인**: 3단계 카드가 여전히 그 값으로 채워진다. **이름이 아니라 ID로 가리키는지
     보는 절이다.**
6. 켜기 전에 있던 카드들을 본다.
   - **확인**: 유형이 채워지지 않았다. 소급하지 않는다. (FR-012)

## 6. 접근 규칙과 함께 (P2)

research R5

1. 유형 속성에 접근 규칙을 하나 건다 (예: 특정 본부는 `Tasks`만).
2. 그 본부 계정으로 하위 카드를 만든다.

3. 규칙이 없는 계정으로 만든다.
   - **확인**: 단계 값이다.

## 8. 품질 게이트

**이번에는 서버 게이트도 걸린다.**

```bash
make webapp-ci
make server-lint
make server-test      # CI가 집행하지 않는다 — 로컬 출력을 근거로 제시한다
```

기준선에서도 실패가 있으므로 **개수가 아니라 실패 목록 diff로 판정한다.** webapp은 세
단계를 따로 돌려 대조한다.

```bash
cd webapp
npm run check
npm run test
npm run check-types
```

기준선은 `main`에서 같은 명령을 돌려 얻는다. server는 `go test -race ./...`의 실패
패키지 목록을 대조한다.
