# Feature Specification: OKR Board로 사용

**Feature Branch**: `008-okr-board-mode`

**Created**: 2026-08-14

**Status**: Draft

**Input**: User description: "보드 공유 속성 기준 카드 접근 권한 섹션 위에 OKR Board로 사용 체크 기능 추가. 체크하면 속성 이름 유형, 속성 값 Objective/Key Results/Tasks 자동으로 만들어짐. 1단계 카드 Objective 2단계 Key Results 3~5단계 Tasks. 새 카드, 새 하위 카드 만들기할 때 자동으로 채워지는 조건이며 무조건 유지되야 하는 필수 조건은 아님"

FY27 KKV OKR 보드는 이미 OKR 사다리를 손으로 세워 쓴다. `유형` 속성을 만들고
`Object`·`Key Results`·`Tasks`를 넣은 뒤, 카드를 만들 때마다 단계에 맞는 값을 사람이
고른다. 카드가 129장이면 129번 고른 것이다.

**하위 카드는 더 나쁘다.** 부모 값을 그대로 물려받아 Object 카드 밑에 또 Object가
생긴다. 이 문제는 이미 알려져 있다 — 서버 코드에 "부모를 통째로 물려받는 것이 OKR
사다리를 망가뜨렸다"는 주석이 있고, 카드 접근 규칙이 걸린 보드에서만 고쳐진다.
규칙을 쓰지 않는 보드는 여전히 사람이 매번 고친다.

이 기능은 보드에 "이건 OKR 보드다"라고 한 번 표시하게 하고, 그다음부터 단계를
자동으로 채운다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 보드를 OKR 보드로 표시한다 (Priority: P1)

기획자가 공유 대화상자를 열고 "OKR Board로 사용"을 켠다. 유형 속성이 준비된다 —
없으면 만들어지고, 이미 손으로 만들어 둔 것이 있으면 그것을 쓴다.

**Why this priority**: 표시가 없으면 채울 근거가 없다. 나머지 이야기가 전부 이
위에 선다.

**Independent Test**: 속성이 없는 보드와 이미 있는 보드 각각에서 체크를 켜고, 유형
속성과 세 값이 준비되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 공유 대화상자, **When** 사용자가 열면, **Then** 카드 접근 권한 섹션 **위에** "OKR Board로 사용" 체크가 있다
2. **Given** 유형 속성이 없는 보드, **When** 체크를 켜면, **Then** `유형` 속성이 생기고 값이 Objective·Key Results·Tasks 셋이다
3. **Given** 이름이 `유형`인 선택 속성이 이미 있는 보드, **When** 체크를 켜면, **Then** 새 속성을 만들지 않고 그 속성을 쓴다
4. **Given** 그 속성의 값이 `Object`인 보드, **When** 체크를 켜면, **Then** 이름이 `Objective`로 바뀌고 **그 값을 쓰던 카드는 값을 잃지 않는다**
5. **Given** 값이 하나도 없는 유형 속성, **When** 체크를 켜면, **Then** 세 값이 채워진다
6. **Given** 체크가 켜진 보드, **When** 다시 열면, **Then** 체크가 켜진 채로 보인다

---

### User Story 2 - 새 카드가 단계에 맞게 시작한다 (Priority: P2)

기획자가 카드를 만든다. 유형을 고르지 않았는데 Objective로 시작한다. 그 카드 밑에
하위 카드를 만들면 Key Results로, 그 밑은 Tasks로 시작한다.

**Why this priority**: 이 기능의 값어치가 여기서 나온다. 다만 US1 없이는 채울 값이
없다.

**Independent Test**: 체크를 켠 보드에서 최상위 카드와 하위 카드를 만들고, 유형이
단계에 맞게 채워졌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 체크가 켜진 보드, **When** 최상위 카드를 만들면, **Then** 유형이 Objective다
2. **Given** Objective 카드, **When** 그 밑에 하위 카드를 만들면, **Then** 유형이 Key Results다
3. **Given** Key Results 카드, **When** 그 밑에 하위 카드를 만들면, **Then** 유형이 Tasks다
4. **Given** Tasks 카드, **When** 그 밑에 또 하위 카드를 만들면, **Then** 유형이 Tasks다
5. **Given** 본부·부서 값이 있는 부모 카드, **When** 하위 카드를 만들면, **Then** 본부·부서는 그대로 내려오고 유형만 단계 값으로 바뀐다
6. **Given** 체크가 꺼진 보드, **When** 카드를 만들면, **Then** 유형이 비어 있다
7. **Given** 카드를 만드는 어느 입구든, **When** 카드를 만들면, **Then** 결과가 같다
8. **Given** 유형 값이 없는 템플릿, **When** 그 템플릿으로 카드를 만들면, **Then** 유형이 Objective다
9. **Given** 유형이 Key Results로 박힌 템플릿, **When** 그 템플릿으로 카드를 만들면, **Then** Key Results다 — 단계가 템플릿을 덮지 않는다

---

### User Story 3 - 채워진 값을 마음대로 바꾼다 (Priority: P2)

팀장이 3단계 카드의 유형을 Key Results로 바꾼다. 그대로 남는다. 값 목록에 `검토`를
하나 더 만들어 쓰기도 한다.

**Why this priority**: "자동으로 채워지되 강제는 아니다"가 이 기능의 성격을 정한다.
US2와 사실상 한 몸이라 같은 우선순위다.

**Independent Test**: 자동으로 채워진 카드의 유형을 바꾸고, 다시 열거나 다른 카드를
만들어도 되돌아가지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 자동으로 채워진 카드, **When** 사용자가 유형을 다른 값으로 바꾸면, **Then** 바뀐 값이 유지된다
2. **Given** 유형을 비운 카드, **When** 다시 열면, **Then** 비어 있는 채다
3. **Given** 유형 속성, **When** 사용자가 값을 추가하거나 이름을 바꾸면, **Then** 단계 자동 채움은 계속 동작한다
4. **Given** 체크를 끈 보드, **When** 확인하면, **Then** 속성도 카드 값도 그대로 남고 새 카드만 비어서 시작한다

---

### Edge Cases

- **이름이 `유형`인 속성이 선택 유형이 아니면?** 그 속성은 쓰지 않는다. 텍스트나 날짜
  속성에 단계 값을 넣을 수 없다.
- **`유형` 속성이 두 개면?** 앞에 있는 것을 쓴다. 어느 쪽이든 사용자가 뒤에 바꿀 수
  있고, 골라 달라고 묻는 화면을 세우는 비용이 이득보다 크다.
- **값 이름을 바꾸면?** 단계는 유지된다. 설정이 이름이 아니라 값 자체를 가리킨다.
- **단계로 쓰던 값을 지우면?** 그 단계는 채우지 못한다. 없는 값을 새로 만들지 않는다 —
  지운 것은 사용자의 결정이다.
- **최대 깊이(5)를 넘으려 하면?** 지금처럼 하위 카드가 만들어지지 않는다. 이 기능은
  깊이 규칙을 바꾸지 않는다.
- **이미 유형 값이 있는 채로 카드가 만들어지면?** 덮어쓰지 않는다. 필터나 그룹으로
  들어온 값, 템플릿에 박힌 값이 우선이다.
- **템플릿으로 카드를 만들면?** 같은 규칙이 걸린다. 템플릿에 유형 값이 없으면 단계에
  맞게 채워지고, 있으면 템플릿 값을 쓴다.
- **하위 카드로 템플릿을 만들었으면?** 그 템플릿은 원래 카드의 깊이를 물려받는다.
  단계를 만들어진 카드에서 읽으므로 3단계 템플릿으로 만든 카드는 Tasks로 시작한다.
  "템플릿은 1단계"라고 가정하면 틀리는 자리다.
- **하위 카드를 템플릿으로 만들 수 있나?** 없다. 하위 카드를 만드는 길에는 템플릿을
  받는 자리가 없다.
- **체크를 켰다 껐다 다시 켜면?** 같은 속성과 값을 다시 쓴다. 중복해서 만들지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 보드 공유 대화상자의 카드 접근 권한 섹션 **위에** "OKR Board로 사용" 켜고 끄기가 있다.
- **FR-002**: 켜면 유형 속성이 준비된다 — 이름이 `유형`인 선택 속성이 있으면 그것을 쓰고, 없으면 만든다.
- **FR-003**: 준비된 속성에는 1단계·2단계·3단계 값이 있다. 기본 이름은 Objective, Key Results, Tasks다.
- **FR-004**: 이미 있는 값의 이름이 다르면 이름만 맞춘다. **그 값을 쓰던 카드는 값을 잃지 않는다.**
- **FR-005**: 어느 값이 어느 단계인지는 이름이 아니라 값 자체로 기억한다. 사용자가 이름을 바꿔도 단계가 유지된다.
- **FR-006**: 새 카드를 만들 때 카드의 단계에 맞는 유형 값이 채워진다 — 1단계 Objective, 2단계 Key Results, 3단계 이상 Tasks. **빈 카드로 만들든 템플릿으로 만들든 같다.**
- **FR-006a**: 단계는 만들어진 카드에서 읽는다. 템플릿으로 만든 카드가 1단계라고 가정하지 않는다 — 하위 카드로 만든 템플릿은 그 깊이를 그대로 물려준다.
- **FR-007**: 새 하위 카드를 만들 때도 같은 규칙으로 채워진다.
- **FR-008**: 하위 카드가 부모에게서 물려받던 다른 속성(본부·부서 등)은 그대로 내려온다. 유형만 단계 값으로 바뀐다.
- **FR-009**: 카드를 만들 때 이미 유형 값이 정해져 있으면 덮어쓰지 않는다. **템플릿이 유형 값을 갖고 있으면 그 값이 이긴다** — 템플릿에 값을 박아 둔 것은 사용자의 명시적 의도이고, 단계 채움은 시작값이다.
- **FR-010**: 만든 뒤 사용자가 바꾼 유형 값은 되돌아가지 않는다. 자동 채움은 시작값이지 유지 조건이 아니다.
- **FR-011**: 끄면 자동 채움만 멈춘다. 속성도 카드에 적힌 값도 그대로 남는다.
- **FR-012**: 자동 채움은 새로 만드는 카드에만 적용된다. 이미 있는 카드는 건드리지 않는다.
- **FR-013**: 카드를 만드는 화면이 어디든 결과가 같다.

### Key Entities

- **OKR 보드 표시**: 보드 하나가 기억하는 설정. 어느 속성을 단계로 쓰는지, 어느 값이
  1·2·3단계인지 가리킨다. 켜지지 않은 보드에는 없다.
- **유형 속성**: 카드의 단계를 적는 선택 속성. 이 기능이 만들 수도, 이미 있던 것을
  쓸 수도 있다. 만든 뒤에는 보통 선택 속성과 다르지 않다 — 값을 더하고 이름을 바꾸고
  색을 고를 수 있다.
- **카드의 단계**: 카드가 트리에서 얼마나 깊은지. 최상위가 1단계다. 이 기능이 만드는
  것이 아니라 이미 있는 것을 읽는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 체크를 켜고 카드 세 단계를 만드는 동안, 사용자가 유형을 고르는 횟수는 0이다.
- **SC-002**: 이미 유형 속성을 손으로 만들어 쓰던 보드에서 체크를 켰을 때, 값을 잃는 카드가 0장이다.
- **SC-003**: 하위 카드에서 부모의 본부·부서가 내려오지 않는 경우가 0건이다.
- **SC-004**: 자동으로 채워진 값을 사용자가 바꾼 뒤 되돌아가는 경우가 0건이다.
- **SC-005**: 카드를 만드는 **모든 입구**에서 결과가 같다 — 빈 카드와 템플릿, 그리고 표·칸반·갤러리·달력·헤더 어디서 눌러도 단계 값이 어긋나는 경우가 0건이다.
- **SC-006**: 005·006·007 시나리오 회귀 0건.

## 범위 밖

- **기존 카드 소급 적용** — 켜는 순간 이미 있는 129장을 채우지 않는다. 사람이 손으로
  적은 값을 기계가 덮는 일이 된다.
- **값 강제** — 3단계 카드를 Objective로 바꿔도 막지 않는다.
- **옮길 때 다시 계산** — 카드를 다른 부모 밑으로 옮기거나 들여쓰기를 바꿔도 유형은
  그대로다. 자동 채움은 만들 때 한 번이다.
- **복제·가져오기·실행 취소** — 이 경로들은 건드리지 않는다.
- **깊이 규칙 변경** — 최대 깊이와 하위 카드 규칙은 그대로다.
- **OKR 관련 다른 기능** — 진척률, 기간, 상위-하위 집계 같은 것은 이 기능이 아니다.

## Assumptions

- 카드의 단계는 이미 시스템이 알고 있다. 이 기능은 그것을 읽기만 한다.
- 체크를 켜고 끌 수 있는 사람은 보드 속성을 바꿀 수 있는 사람과 같다.
- 속성 이름 `유형`과 값 이름 Objective·Key Results·Tasks는 화면 언어와 무관하게
  같은 문자열을 쓴다. 기존 보드가 그렇게 쓰고 있고, 번역하면 이미 만들어 둔 속성을
  못 알아본다.
- 3단계 이상은 모두 Tasks다. 4단계와 5단계를 따로 나눌 이유가 아직 없다.
- 005·006·007이 정한 조직 속성의 동작은 그대로다.
