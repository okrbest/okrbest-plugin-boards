# 계약: OKR Board 표시와 단계 채움

**Feature**: `008-okr-board-mode`

설정과 채움이 기존 코드와 맺는 계약이다. 저장 형태와 규칙은
[data-model.md](../data-model.md)에 있고, 여기서는 **어느 코드가 무엇을 책임지는가**를
정한다.

---

## 1. 규칙은 양쪽에 같은 모양으로 산다

이 기능의 규칙은 서버와 클라이언트 둘 다 안다. 언어가 다르므로 코드를 공유할 수 없고,
**같은 규칙을 두 번 쓴다.** 대신 규칙을 아주 작게 유지한다.

| 규칙 | 서버 | 클라이언트 |
|---|---|---|
| 설정 읽기 | `model/okr_board.go` | `src/okrBoard.ts` |
| 깊이 → 옵션 ID | 같은 파일 | 같은 파일 |
| 설정 쓰기 | **하지 않는다** | `mutator` |
| 채우기 | 하위 카드만 | 빈 카드와 템플릿 카드 |

서버는 설정을 **읽기만 한다.** 켜고 끄는 것은 보드를 편집하는 행위이고 기존 보드 patch
경로로 간다 — 새 엔드포인트를 만들지 않는다.

두 구현이 갈라지지 않게 하는 것은 시험이다. 같은 입력(깊이·설정)에 같은 옵션 ID가
나오는지를 양쪽에서 각각 확인한다.

---

## 2. 설정

`board.properties.okrBoard`. 형태는 [data-model.md](../data-model.md) 1절.

| | 방법 |
|---|---|
| 읽기 (Go) | `PropertyAccessSettingsFromProperties`와 같은 JSON 재인코딩. 없으면 nil, 깨졌으면 도메인 오류 |
| 읽기 (TS) | 형태를 확인하고 아니면 "설정 없음"으로 떨어뜨린다 |
| 쓰기 | 보드를 복제해 키를 갈아 끼우고 보드 갱신 한 번 |
| 끄기 | 키를 지운다 |
| 권한 | 보드를 편집할 수 있으면 켜고 끌 수 있다 |

**한 번의 쓰기로 끝낸다.** 속성 준비와 설정 저장이 같은 보드 갱신에 실린다. 나눠 쓰면
실행 취소가 여러 단계가 되고, 중간 상태(속성은 생겼는데 설정이 없는 보드)가 저장된다.

---

## 3. 유형 속성 준비

켤 때 한 번만 이름 `유형`으로 찾는다. 그 뒤로는 설정의 ID로만 움직인다
([research.md](../research.md) R7).

| 조건 | 결과 |
|---|---|
| 이름이 `유형`인 **선택** 속성 | 그것을 쓴다 |
| 이름이 같지만 선택 속성이 아니다 | 무시하고 새로 만든다 |
| 둘 이상 | 앞의 것을 쓴다 |
| 값이 모자라다 | 뒤에 더한다 |
| 값 이름이 다르다 | **옵션 ID를 유지한 채 이름만 바꾼다** |

옵션을 지우고 새로 만들지 않는다. 카드가 옵션 ID를 저장하므로 지우면 값을 잃는다.

## 4. 클라이언트가 만드는 카드 — 빈 카드와 템플릿

`centerPanel`에 입구가 둘이다. **둘 다 채운다.**

| 함수 | 언제 | 깊이 |
|---|---|---|
| `addCard` | 빈 카드 | 새 카드라 0 |
| `addCardFromTemplate` | 보기에 기본 템플릿이 있거나 사용자가 템플릿을 고를 때 | **복제된 카드에서 읽는다** |

`addCard`는 기본 템플릿이 걸려 있으면 첫 줄에서 `addCardFromTemplate`으로 빠져나간다.
그러므로 채움을 `addCard` 안쪽에만 두면 **기본 템플릿이 있는 보기에서는 한 번도 돌지
않는다.**

| 조건 | 결과 |
|---|---|
| 설정 없음 | 아무것도 하지 않는다 |
| 그 속성에 이미 값이 정해짐 | **덮지 않는다** — 필터·그룹·템플릿이 정한 값이 이긴다 |
| 그 외 | `levels[깊이]`를 넣는다 |

**깊이를 0으로 가정하지 않는다.** 서버의 블록 복제는 `depth`와 `parentCardId`를
그대로 복사한다. 카드 상세의 "New template from card"는 하위 카드에서도 열리므로,
3단계 카드로 만든 템플릿은 `depth: 2`를 물려준다. 그 템플릿으로 만든 카드는 Tasks로
시작해야 맞다.

템플릿에 유형 값이 박혀 있으면 그것이 이긴다. 템플릿의 값은 사용자가 명시적으로 정한
것이고, 단계 채움은 시작값이다(FR-009, FR-010).

`duplicateCard`가 복제 직후 보내는 속성 덮어쓰기 자리에 실으면 된다 — 필터·그룹 값이
이미 그 길로 간다.

## 5. 하위 카드 — 서버

`app/cards.go`의 `CreateSubCard`. 부모 속성을 복사하는 블록 **안**, 접근 규칙 기본값을
채우기 **직전**이다.

```
callerChoseProperties 아님
  → 부모 속성 복사
  → OKR 단계 값으로 유형을 덮는다      ← 이번에 넣는 자리
  → 접근 규칙 기본값
```

| 조건 | 결과 |
|---|---|
| 설정 없음 | 지금과 같다 |
| 설정 있음 | 유형만 `levels[깊이]`로 바꾼다 |
| 부모의 다른 속성 | **그대로 내려온다** — 이 기능이 끊으면 안 되는 동작(FR-008) |
| 클라이언트가 속성을 보냄 | 지금과 같다 — 부모 복사도 단계 채움도 하지 않는다 |
| 접근 규칙 기본값이 유형을 정함 | **규칙이 이긴다** (research R5) |

**클라이언트는 하위 카드의 유형에 관여하지 않는다.** 속성을 실어 보내는 순간 서버가
부모 상속 블록 전체를 건너뛰어 본부·부서가 안 내려간다.

## 6. 공유 대화상자

`shareBoard.tsx`의 `<PropertyAccessSection>` **바로 위**에 섹션을 하나 끼운다.

접근 규칙 섹션이 쓰는 모양(제목 + 설명 한 줄 + 스위치)을 차용한다. **새 SCSS 파일도
새 위젯도 만들지 않는다**(원칙 II).

---

## 7. i18n

체크박스 제목과 설명만 `en.json`·`ko.json`에 넣는다.

**속성 이름 `유형`과 값 이름 `Objective`·`Key Results`·`Tasks`는 번역하지 않는다.**
화면 언어에 따라 달라지면 이미 만들어 둔 속성을 못 알아보고, 언어를 바꾼 사용자의
보드에서 단계가 멈춘다.
