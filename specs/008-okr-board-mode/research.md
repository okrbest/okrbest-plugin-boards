# Phase 0 연구: OKR Board로 사용

**Feature**: `008-okr-board-mode`

명세에 `[NEEDS CLARIFICATION]`이 없다. 갈림길 셋(속성 재사용, 값 이름 통일, 끄기
동작)은 명세 전에 정했다. 이 문서가 푸는 것은 **어떻게 만들 것인가**다.

---

## R1. 설정을 어떤 형태로 저장하나

**결정**: `board.properties`에 키 하나를 두고, 속성 ID와 단계별 **옵션 ID**를 적는다.

```jsonc
"okrBoard": {
  "propertyId": "<유형 속성 ID>",
  "levels": ["<1단계 옵션 ID>", "<2단계 옵션 ID>", "<3단계 옵션 ID>"]
}
```

**근거**: 이름으로 기억하면 깨진다. 사용자가 `Tasks`를 `할 일`로 바꾸는 순간 3단계를
못 찾는다(FR-005). 옵션 ID는 이름을 바꿔도, 색을 바꿔도, 순서를 바꿔도 같다.

`levels`를 배열로 두는 이유는 3단계 이상이 전부 같은 값이기 때문이다 — 깊이를 인덱스로
쓰고 배열 끝을 넘으면 마지막 항목을 쓴다. 깊이가 늘어도 규칙이 그대로다.

자리는 `propertyAccess`(002)와 `orgColors`(007)가 이미 사는 곳이다. 읽기·쓰기·실행
취소·웹소켓이 그 경로에서 따라온다. Go 쪽 읽기도 `PropertyAccessSettingsFromProperties`가
쓰는 JSON 재인코딩 방식을 그대로 베낀다.

**대안**:

- **이름으로 저장** — 사용자가 값 이름을 바꿀 수 있다는 요구(FR-005)와 정면으로 어긋난다.
- **속성 템플릿에 표시 필드 추가** — `IPropertyTemplate`에 비표준 필드를 넣으면 업스트림
  머지에서 계속 부딪힌다. 보드 설정은 보드 설정 자리에 둔다.
- **단계마다 키를 따로**(`objectiveId`, `keyResultId`, `taskId`) — 4단계를 따로 두고
  싶어지면 키를 또 만들어야 한다. 배열이면 그때 원소만 는다.

---

## R2. 켤 때 몇 번 쓰나

**결정**: 한 번. 유형 속성 준비와 설정 저장을 **하나의 보드 갱신**으로 보낸다.

**근거**: 켜는 동작이 하는 일은 셋이다 — 속성 만들거나 찾기, 값 채우거나 이름 맞추기,
설정 적기. 기존 뮤테이터를 이어 붙이면 `insertPropertyTemplate` + `insertPropertyOption`
×3 + 설정 저장으로 **다섯 번 쓰기, 다섯 단계 실행 취소**가 된다. 사용자가 Ctrl+Z를
다섯 번 눌러야 원래대로 돌아간다.

보드 객체를 복제해 `cardProperties`와 `properties`를 함께 고친 뒤 한 번 보내면 한
단계다. 접근 규칙 섹션이 이미 이 방식으로 저장한다.

**대안**: 기존 뮤테이터 조합. 코드는 짧지만 실행 취소가 사용자에게 이상하게 보인다.

---

## R3. 기존 값 이름을 어떻게 맞추나

**결정**: 옵션 ID를 유지한 채 `name`만 바꾼다.

**근거**: 카드는 옵션 ID를 저장한다. FY27 보드의 129장이 `Object` 옵션의 ID를 들고
있으므로, 이름만 `Objective`로 바꾸면 **값을 하나도 잃지 않는다**(FR-004, SC-002).
007에서 조직 색을 다루며 확인한 구조다.

옵션을 지우고 새로 만들면 129장이 값을 잃는다. 그건 사용자가 손으로 적은 것을 기계가
버리는 일이다.

**대안**:

- **새 옵션 추가하고 기존 것은 둔다** — 목록에 `Object`와 `Objective`가 나란히 남아
  같은 뜻의 값이 둘이 된다.
- **이름을 안 건드리고 `Object`를 1단계로 쓴다** — 사용자가 "Objective로 통일"을 골랐다.

---

## R4. 하위 카드를 왜 서버가 채우나

**결정**: 최상위는 클라이언트(`addCard`), 하위는 서버(`CreateSubCard`).

**근거**: 서버 코드가 이렇게 생겼다.

```go
callerChoseProperties := len(card.Properties) > 0
if !callerChoseProperties {
    card.Properties = deepCopyProperties(parentCard.Properties)   // 부모 상속
    fillDefaultConditionValues(...)                                // 규칙 기본값
}
```

**클라이언트가 유형 하나를 실어 보내면 이 블록 전체가 건너뛰어진다.** 본부·부서가
하위 카드로 안 내려간다 — 005가 만든 동작이 끊긴다. 명세가 FR-008로 못박고 SC-003으로
재는 회귀가 바로 이것이다.

서버에서 채우면 부모 복사가 그대로 돌고 유형만 덮어쓴다. 게다가 이 자리는 서버 주석이
"부모를 통째로 물려받는 것이 OKR 사다리를 망가뜨렸다"고 적어 둔 곳이라, 같은 문제의
해결을 같은 곳에 두게 된다.

최상위는 반대다. 서버가 채우려면 `InsertBlocks`에 훅을 걸어야 하는데 그 경로는
가져오기·복제·실행 취소도 지난다. 카드를 복제했더니 유형이 바뀌는 놀람이 생긴다.

**대안**:

- **전부 클라이언트** — 위 회귀를 만든다. 막으려면 클라이언트가 부모 속성을 직접
  복사해 보내야 하는데, 그러면 상속 규칙이 서버와 클라이언트 두 곳에 생긴다.
- **전부 서버** — 최상위 경로가 지저분해진다.
- **서버 게이트를 "속성별"로 바꾼다** — `callerChoseProperties`를 속성 단위로 쪼개면
  전부 클라이언트가 가능해진다. 002가 세운 판정 흐름을 건드리는 변경이라 이 기능의
  값어치에 비해 위험이 크다.

## R5. 접근 규칙과 순서가 어떻게 되나

**결정**: 부모 복사 → **OKR 단계** → 접근 규칙 기본값. 규칙이 마지막에 덮는다.

**근거**: 둘은 성격이 다르다. 접근 규칙의 기본값은 "이 사람이 만들 수 있는 카드"를
정하는 **권한**이고(002), OKR 단계는 "보통 이 값으로 시작한다"는 **편의**다. 권한이
편의를 이겨야 한다.

이건 가상의 충돌이 아니다. FY27 보드에는 유형 속성에 걸린 접근 규칙이 3개 있다. 규칙이
"당신은 Tasks만"이라고 정했는데 OKR 단계가 Objective로 덮으면, 사용자는 만들자마자
고칠 수 없는 카드를 얻는다.

**대안**: OKR 단계를 마지막에 둔다. 단계는 항상 맞지만 규칙을 넘는 카드가 생긴다.

---

## R6. 이미 값이 있으면 어떻게 아나

**결정**: 최상위는 채우기 직전에 그 속성 값이 비었는지 보고, 하위는 부모 복사 뒤 값이
있어도 유형만 덮는다.

**근거**: 두 경로에서 "이미 있다"의 뜻이 다르다.

- **최상위**: 필터나 그룹이 값을 정해 준 경우다(`propertiesThatMeetFilters`). 사용자가
  `유형 = Tasks` 필터를 걸어 둔 화면에서 카드를 만들면 그 의도가 우선이다(FR-009).
- **하위**: 부모에게서 복사돼 온 값이다. 그건 사용자의 의도가 아니라 상속의 부산물이고,
  덮지 않으면 Object 밑에 Object가 생기는 원래 문제로 돌아간다.

**대안**: 양쪽을 같게 다룬다. 어느 쪽으로 통일해도 한쪽이 틀린다.

---

## R7. 유형 속성을 어떻게 알아보나

**결정**: 켤 때 한 번만 이름 `유형`으로 찾는다. 그 뒤로는 설정에 적힌 ID로만 움직인다.

**근거**: 이름 대조는 "이미 손으로 만들어 쓰던 보드를 알아본다"는 목적에만 필요하다.
켠 뒤에는 사용자가 속성 이름을 바꿔도 설정이 ID를 들고 있으므로 계속 동작한다.

이름이 `유형`인데 선택 속성이 아니면 쓰지 않는다. 텍스트나 날짜 속성에 단계 값을 넣을
수 없다. 그런 보드에서는 새 속성을 만든다.

**대안**: 매번 이름으로 찾는다. 사용자가 속성 이름을 바꾸면 기능이 멈춘다.
