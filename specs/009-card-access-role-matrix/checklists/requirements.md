## 검증 기록

**1회차 — 통과.** 확인한 자리는 셋이다.

1. **구현 세부 누출** — FR 어디에도 필드명·타입·파일 경로를 쓰지 않았다. "규칙은 묶음을
   가리킨다"까지만 적고 참조를 어떻게 저장할지는 적지 않았다. 데이터 모양은
   `/speckit-plan`이 정한다.
2. **성공 기준의 측정 가능성** — SC 일곱 개가 전부 세는 값이다. "12칸 중 몇 칸",
   "여섯 줄", "0줄", "1회", "0건", "1곳". SC-007만 세는 값이 아니라 시점("저장 전에")인데,
   보이느냐 안 보이느냐로 판정되므로 검증 가능하다.
3. **명확화 표시** — 애매했던 세 자리를 명세 안에서 기본값으로 닫았다. 근거를 남긴다.
   - 조직 속성이 둘 이상인 보드 → 규칙이 지정하고, 하나뿐이면 화면이 자동으로 고른다
     (FR-006). 사용자에게 물을 만큼 갈림길이 크지 않다.
   - OKR Board가 아닌 보드의 표 → 행이 정해지지 않으므로 표를 안 준다 (FR-022).
   - 기존 절대값 규칙 → 관계로 옮기지 않고 둘 다 지원한다 (FR-001). 의미가 달라 기계적
     변환이 불가능하고, 이미 쓰는 보드가 있다.

**2회차 — 계획 단계에서 드러난 것을 반영한 뒤 다시 통과.**

`/speckit-plan`이 SC-004를 못 지킨다고 보고했다. 원인은 직책 묶음을 보드마다 저장하기로
한 것이었다 — 보드를 만들 때마다 배정을 반복해야 하니 "스위치 1회"가 어느 보드에서도
성립하지 않았다.

저장 자리를 팀으로 옮겨 해결했다. 근거는 셋이다.

1. 묶음은 회사 조직 구조지 보드 설정이 아니다. 보드마다 다르면 같은 사람이 보드마다
   권한이 다른데 아무도 모른다
2. 조직 마스터를 이미 팀 단위로 읽는다. 묶음만 보드에 두면 같은 성격의 값이 갈린다
3. `focalboard_teams.settings`가 이미 있어 마이그레이션이 없다

따라온 결정이 하나 있다. 묶음이 팀 것이 되면 한 사람의 편집이 팀의 모든 보드에 걸리므로,
편집 권한을 보드 관리자에서 **시스템 관리자·팀 관리자**로 올렸다(FR-011b). 이 플러그인은
두 역할을 이미 구분해 판정하고 있어 새 권한 개념을 만들지 않았다.

SC-004는 "묶음이 정해진 팀에서"라는 조건을 달았다. 조건이 없으면 첫 보드에서 반드시
거짓이 되는 기준이 된다 — 묶음은 이름으로 추정할 수 없어 자동으로 못 만든다(research R9).
