# Phase 0 조사: 카드 접근 권한을 역할 매트릭스로 정한다

기존 코드를 읽고 정한 것들이다. 각 항목은 결정 · 근거 · 버린 안 순서로 적는다.

---

## R1. 관계를 규칙 어디에 두나

**결정.** 기존 `divisionId` · `departmentId` 옆에 `relation` 필드를 더한다. `relation`이
비어 있으면 지금처럼 절대값으로 읽는다. 값이 있으면 절대값 두 칸을 무시한다.

**근거.** 규칙 종류를 둘로 나누면 평가기가 두 갈래를 각각 돌아야 하고, 저장 형식도
둘이 된다. 한 필드를 더하면 기존 규칙은 `relation`이 없는 규칙일 뿐이라 읽는 코드가
갈라지지 않는다. FR-001의 "기존 규칙 판정 결과가 안 바뀐다"가 코드 구조로 보장된다.

**버린 안.** 절대값을 관계로 자동 변환 — 의미가 다르다. `divisionId=영업본부`는 "영업본부
사람에게"이고 `relation=같은 본부`는 "카드와 같은 본부 사람에게"다. 영업본부 사람이 보는
개발본부 카드에서 둘의 답이 갈린다. 기계로 옮길 수 없다.

## R2. 게이트를 규칙 단위로 옮긴다

**결정.** 평가를 `gates`/`grants` 두 map 조회에서 규칙 루프로 바꾼다.

지금은 조건 키가 `(속성ID, 값ID)`이고 여러 규칙이 같은 키에 병합된다
([property_access.go:320-353](../../server/app/property_access.go#L320-L353)). 관계 조건은
카드마다 답이 달라 미리 계산해 둘 수 없고, 카드 쪽 값이 여럿이 되면(FR-008) 한 규칙이
여러 키에 걸린다. 병합한 뒤에는 어느 규칙에서 왔는지 잃어버려 규칙 단위 판정이 불가능하다.

바꾼 뒤 한 카드를 판정하는 순서는 이렇다.

```
mentioned = false        // 규칙이 이 카드를 언급했나
gated     = false        // 언급한 규칙 중 조직 조건이 붙은 게 있나
passed    = false        // 나를 통과시킨 규칙이 있나
granted   = none

각 규칙마다:
    카드 쪽 조건이 안 맞으면 건너뛴다
    mentioned = true
    조직 조건(절대값이든 관계든)이 붙어 있으면 gated = true
    사람 쪽 조건이 다 맞으면:
        passed = true
        granted = max(granted, 규칙 권한)

mentioned가 false → max(조회, 작성자 바닥)      // 규칙 밖의 카드 (기존 FR-015)
gated이고 passed가 false → 전체보기 바닥        // 매트릭스의 빈칸 (FR-009)
그 외 → max(granted, 전체보기 바닥, 작성자 바닥)
```

**근거.** 지금 코드의 세 갈래를 그대로 보존한다. 특히 **작성자 바닥이 게이트 안쪽에
있다**는 배치를 유지한다 — 게이트가 닫히면 작성자 바닥을 안 준다. 안 그러면 다른 본부
값을 적은 카드를 만들어 게이트를 통과하는 길이 열린다
([property_access.go:26-32](../../server/app/property_access.go#L26-L32)).

**관계 조건도 조직 조건으로 센다.** `gated`는 "조직을 따지는 규칙이 이 카드를 언급했나"이고,
관계는 조직을 따지는 방식 중 하나다. 이걸 안 세면 팀원이 타 본부 Objective를 볼 때
`gated=false` 갈래로 빠져 조회 권한이 새어 나간다 — FR-009가 깨진다.

**버린 안.** 관계 조건만 별도 경로로 판정하고 기존 map은 둔다 — 두 경로의 게이트를
어떻게 합칠지가 매번 결정 사항이 되고, 그 결정이 코드 두 곳에 갈라져 남는다.

## R3. 관계 판정에 쓰는 값

**결정.**

| 관계 | 카드에서 읽는 값 | 보는 사람에게서 읽는 값 | 성립 조건 |
|---|---|---|---|
| 전체 | — | — | 항상 |
| 같은 본부 | 규칙이 지정한 `orgDivision` 속성 | 조직 배정의 소속 단위와 그 조상 | 카드 값이 조상 집합에 있다 |
| 다른 본부 | 같음 | 같음 | 양쪽 다 값이 있고, 카드 값이 조상 집합에 **없다** |
| 같은 부서 | 규칙이 지정한 `orgDepartment` 속성 | 같음 | 카드 값이 조상 집합에 있다 |
| 본인 | 카드 작성자 + 규칙이 지정한 person 속성 | 사용자 ID | 작성자가 나이거나 그 속성에 내가 있다 |

**근거.** 조상 집합은 이미 있다 — `orgUnitAncestors`가 소속 단위부터 뿌리까지 올라간다
([org_master.go:80](../../server/app/org_master.go#L80)). 부서 소속자가 본부 조건에 걸리는
동작이 기존 절대값 규칙과 같아진다(FR-017). 새 개념을 안 만든다.

조직 속성이 담는 값은 `OrgUnits.id`고, 조직 배정도 같은 ID를 쓴다. 변환이 없다
([property_access.go:50-55](../../server/app/property_access.go#L50-L55)).

**다른 본부는 같은 본부의 부정이 아니다.** 카드에 본부 값이 없으면 둘 다 성립하지
않는다(FR-007). 부정으로 두면 값 없는 카드가 전부 "다른 본부"가 되어, 방금 만든 빈 카드가
타 본부 규칙에 걸린다.

## R4. 어느 속성을 볼지 규칙이 지정한다

**결정.** 관계 조건이 `orgPropertyId`(본부·부서용)와 `assigneePropertyId`(본인용)를 함께
저장한다. 화면은 보드에 해당 타입 속성이 하나뿐이면 자동으로 채운다.

**근거.** 보드에 `orgDivision` 속성이 둘일 수 있다 — 실제로 "주관 본부"와 "협조 본부"처럼
쓴다. 서버가 첫 번째를 고르면 어느 쪽인지 화면에 안 보이고, 속성 순서가 바뀌면 권한이
말없이 달라진다.

`person`과 `multiPerson` 둘 다 받는다. 저장 형태가 문자열과 배열로 갈리는데,
`eachPropertyValueID`가 이미 둘을 같이 훑는다
([property_access.go:548](../../server/app/property_access.go#L548)).

**버린 안.** 보드에 조직 속성이 하나라는 가정 — 002가 이미 "속성을 지정한다"로 갔고,
같은 이유가 여기에도 그대로 걸린다.

## R5. 직책 묶음은 팀이 기억한다

**결정.** `focalboard_teams.settings`의 `dutyTiers` 키에 `{id, name, dutyIds[]}` 배열로
둔다. 규칙(보드 소유)은 `tierIds`로 가리킨다 — 한 줄이 묶음을 여럿 가리킬 수 있다. 기존
`dutyId`는 그대로 읽는다. 둘 다 있으면 `tierIds`가 이긴다.

**근거.** 셋이다.

1. **묶음은 회사 조직 구조지 보드 설정이 아니다.** 어느 직책이 C-Level인가가 보드마다
   달라질 이유가 없다. 보드마다 저장하면 A 보드는 CTO를 넣고 B 보드는 안 넣는 상태가
   생기고, 같은 사람이 보드마다 권한이 다른데 아무도 모른다.
2. **조직 마스터를 이미 팀 단위로 읽는다.** `GetOrgUnitsForTeam` · `GetDutiesForTeam`이
   그렇다. 묶음만 보드에 두면 같은 성격의 값이 두 자리로 갈린다.
3. **팀에 담을 자리가 이미 있다.** `Team.Settings map[string]interface{}`와
   `upsertTeamSettings`가 있다 ([team.go:59](../../server/services/store/sqlstore/team.go#L59)).
   보드가 `board.properties`를 쓰는 것과 같은 모양이라 **마이그레이션이 없다** — 원칙 VII의
   되돌릴 수 없는 스키마 변경을 피한다.

`dutyId`를 남기는 것이 FR-016이다. 보드를 열었다는 이유로 저장 형식이 바뀌면, 그 보드를
아직 안 연 다른 클라이언트가 규칙을 못 읽는다.

**규칙은 보드에 남는다.** 묶음은 팀 공통이지만 매트릭스 값은 보드마다 다를 수 있다 —
명세가 "기본값은 표준, 보드별 수정 허용"으로 정했다.

**버린 안.** 보드 저장 + "다른 보드에서 가져오기" — 가져온 뒤 원본을 고치면 두 보드가
갈라진다. 갈라진 것을 알아챌 방법이 없다.

## R6. 묶음은 팀 관리자가 고친다

**결정.** 묶음 편집은 **시스템 관리자 또는 팀 관리자**만 한다. 보드 관리자는 보되 못
고친다. 편집 자리는 보드 공유 대화상자 안이고, 권한이 없으면 값이 보이되 잠긴다.

**근거.** 묶음을 팀에 저장하면 한 사람의 편집이 팀의 모든 보드에 걸린다. 지금 접근 규칙
섹션은 보드 관리자(`ManageBoardRoles`)가 여는데
([propertyAccessSection.tsx:143](../../webapp/src/components/shareBoard/propertyAccessSection.tsx#L143)),
그대로 두면 **A 보드 관리자가 B 보드의 권한을 바꾼다.** B 보드 관리자는 모른다.

판정 방법이 이미 있다.

| 구분 | 판정 | 이미 쓰는 곳 |
|---|---|---|
| 시스템 관리자 | `permissions.HasPermissionTo(userID, PermissionManageSystem)` | 별칭이 [permission.go:13](../../server/model/permission.go#L13) |
| 팀 관리자 | `permissions.HasPermissionToTeam(userID, teamID, PermissionManageTeam)` | [boards.go:650](../../server/app/boards.go#L650) |

`boards.go:650`이 **팀 관리자를 보드 관리자로 올려준다.** 이 플러그인은 이미 "팀 관리자 =
그 팀 모든 보드의 관리자"로 취급한다. 묶음 편집을 팀 관리자에게 주는 것이 기존 규칙과
어긋나지 않는다.

**클라이언트는 팀 관리자 여부를 직접 못 본다.** `IUser.roles`는 시스템 역할만 담는다
([user.tsx:19](../../webapp/src/user.tsx#L19)). 서버가 팀 설정을 내려줄 때 `canEdit`
플래그를 함께 준다 — 카드 권한이 이미 `capabilities`를 그렇게 내려보낸다.

**버린 안.** 사이드바 설정 메뉴에 별도 화면 — 지금 그 메뉴에는 가져오기·내보내기·언어·
테마만 있다. 조직 권한이 들어갈 성격이 아니고, 규칙을 짜다 묶음을 확인하러 화면을 나가야
한다.

**버린 안.** 보드 관리자에게 열고 경고만 띄우기 — 경고는 사고를 늦출 뿐 막지 않는다.
권한 설정에서 되돌리기 어려운 실수를 경고로 막는 것은 값이 싸다.

## R7. 표가 만든 줄을 알아본다

**결정.** 규칙에 `source` 필드를 둔다. 표가 만들면 `matrix`, 손으로 만들면 빈 값이다.
표에서 저장할 때 `source=matrix`인 줄만 갈아 끼운다.

**근거.** FR-021이 요구한다. 표가 모르는 줄을 지우면 사용자가 손으로 만든 예외가 말없이
사라진다. 표가 만든 줄을 조건으로 되짚어 찾는 방법도 있지만, 사용자가 그 줄을 한 글자
고치는 순간 되짚기가 실패한다.

## R8. 성능

**결정.** 규칙 루프를 그대로 돈다. 인덱스를 만들지 않는다.

**근거.** 카드 하나 판정 비용이 `O(규칙 수 × 카드 속성 수)`가 된다. 매트릭스가 여섯 줄,
예외를 더해도 스무 줄 안쪽이다. 지금 map 조회가 `O(카드 속성 수)`였으니 상수배 20 정도다.

가장 무거운 자리는 웹소켓 팬아웃이다 — `수신자 × 카드 × 규칙`
([property_access.go:132](../../server/app/property_access.go#L132)). 수신자마다 조상 집합과
직책을 한 번 계산해 두면 규칙 루프 안에는 map 조회와 문자열 비교만 남는다.

**버린 안.** 카드 쪽 조건으로 규칙을 미리 인덱싱 — 규칙이 스무 줄인데 인덱스를 만드는
것은 재는 대신 짐작으로 최적화하는 일이다. `make server-test`의 실행 시간이 눈에 띄게
늘면 그때 다시 본다.

## R9. 묶음은 자동으로 못 만든다

**결정.** 표준 규칙 여섯 줄은 자동으로 깔되, **직책 묶음은 사용자가 만든다.** 이름으로
추정하지 않는다.

**근거.** 규칙 쪽은 자동으로 된다 — OKR 보드가 유형 속성과 세 값을 이미 기억한다(008).
묶음 쪽은 안 된다. 회사마다 직책 이름이 다르고, 어느 직책이 C-Level인지는 이름으로 알 수
없다. 추정이 틀리면 권한이 조용히 잘못 깔린다 — 화면은 멀쩡해 보이고 당사자만 겪는다.

**그래서 SC-004는 "묶음이 정해진 팀에서"라는 조건을 단다.** 묶음이 팀에 저장되므로(R5)
배정은 팀당 한 번이고, 그 뒤로는 보드를 몇 개 만들든 스위치 1회다. 조건을 달지 않으면
첫 보드에서 반드시 거짓이 되는 기준이 된다.

**팀에 묶음이 아직 없는 상태를 화면이 다룬다.** 규칙 여섯 줄은 깔리지만 묶음이 비어
아무에게도 안 걸린다. 켜자마자 "묶음부터 정하세요"를 띄운다.

**버린 안.** 직책 이름에서 등급을 추정 — `CSO`·`CTO`처럼 규칙적인 이름만 맞는다. 한글
직책명(`전무`, `상무`)이나 회사 고유 명칭에서는 전부 틀린다.
