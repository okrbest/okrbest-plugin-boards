# 계약: 카드 접근 권한을 역할 매트릭스로 정한다

구현이 지켜야 하는 약속이다. 각 절이 테스트 하나 이상으로 대응된다.

---

## 1. 판정 순서 (서버)

`PropertyAccessEvaluator.evaluate`가 카드 하나를 판정하는 순서다. 세 갈래를 지금과 똑같이
유지하고, 갈래를 고르는 방식만 map 조회에서 규칙 루프로 바꾼다.

```
관리자면 → 관리
규칙이 꺼져 있으면 → 보드 권한

mentioned, gated, passed = false, false, false
granted = 없음

각 규칙마다:
    카드 쪽 조건 불일치 → 건너뛴다
    mentioned = true
    조직 조건이 붙어 있으면 → gated = true
    사람 쪽 조건 전부 일치 →
        passed = true
        granted = max(granted, 규칙 권한)

mentioned == false          → max(조회, 작성자 바닥)
gated && passed == false    → 전체보기 바닥            ← 작성자 바닥을 주지 않는다
그 외                       → max(granted, 전체보기 바닥, 작성자 바닥)
```

**`gated && !passed`에서 작성자 바닥을 빼는 것이 이 계약의 핵심이다.** 주면 다른 본부
값을 적은 카드를 만들어 게이트를 통과하는 길이 열린다.

**조직 조건이 붙었다**는 다음 중 하나다.

- `divisionId` 또는 `departmentId`가 비어 있지 않다 (기존)
- `relation`이 비어 있지 않다 (신규 — `any` 포함)

### 테스트

| # | 상황 | 기대 |
|---|---|---|
| 1-1 | 규칙이 언급하지 않는 카드 | 조회 |
| 1-2 | 규칙이 언급하지 않는 카드, 내가 작성자 | 편집 |
| 1-3 | 조직 조건이 붙은 규칙이 언급하는데 나를 통과시키지 않음 | 접근 없음 |
| 1-4 | 같은 상황에서 내가 작성자 | **접근 없음** (작성자 바닥 없음) |
| 1-5 | 같은 상황에서 내 직책이 보드 전체보기 | 조회 |
| 1-6 | 두 규칙이 통과시키고 권한이 다름 | 높은 쪽 |

## 2. 관계 판정

| 관계 | 성립 | 불성립 |
|---|---|---|
| `any` | 항상 | — |
| `sameDivision` | 카드 값이 내 조상 집합에 있다 | 없다 / 카드 값 없음 / 내 배정 없음 |
| `otherDivision` | 양쪽 값이 있고 카드 값이 조상 집합에 없다 | 같다 / 어느 쪽이든 값 없음 |
| `sameDepartment` | 카드 값이 내 조상 집합에 있다 | 없다 / 어느 쪽이든 값 없음 |
| `mine` | 작성자가 나이거나 담당자 속성에 내가 있다 | 둘 다 아니다 |

### 테스트

| # | 상황 | 기대 |
|---|---|---|
| 2-1 | 영업본부 소속, 카드 본부 = 영업본부, `sameDivision` | 성립 |
| 2-2 | 영업1팀(영업본부 하위) 소속, 카드 본부 = 영업본부, `sameDivision` | 성립 — 조상을 따라 올라간다 |
| 2-3 | 영업본부 소속, 카드 본부 = 개발본부, `sameDivision` | 불성립 |
| 2-4 | 같은 상황, `otherDivision` | 성립 |
| 2-5 | 카드에 본부 값이 없음, `sameDivision` | 불성립 |
| 2-6 | 카드에 본부 값이 없음, `otherDivision` | **불성립** — 부정이 아니다 |
| 2-7 | 조직 배정이 없는 사용자, 모든 관계 | 불성립 |
| 2-8 | `mine`, 내가 작성자, 담당자 속성 미지정 | 성립 |
| 2-9 | `mine`, 담당자가 나, 작성자는 남 | 성립 |
| 2-10 | `mine`, 담당자가 여럿이고 그중 하나가 나 (multiPerson) | 성립 |

## 3. 필드 우선순위

읽는 쪽이 새 필드를 먼저 보고 없으면 기존 필드로 떨어진다.

| 축 | 새 필드가 있을 때 | 없을 때 |
|---|---|---|
| 카드 값 | `propertyValueIds` | `propertyValueId` |
| 직책 | `tierIds`의 `dutyIds` 합집합 | `dutyId` |
| 조직 | `relation` (절대값 무시) | `divisionId` · `departmentId` |

### 테스트

| # | 상황 | 기대 |
|---|---|---|
| 3-1 | 새 필드가 전부 빈 기존 규칙 | 지금과 같은 판정 |
| 3-2 | `relation`과 `divisionId`가 둘 다 있음 | `relation`으로 판정 |
| 3-3 | `tierIds`와 `dutyId`가 둘 다 있음 | `tierIds`로 판정 |
| 3-4 | `propertyValueIds`에 값 둘, 카드가 그중 하나 | 일치 |

## 4. 저장 검증

| 입력 | 결과 |
|---|---|
| `relation`이 목록에 없는 값 | 400 |
| `relation`이 본부·부서 계열인데 `orgPropertyId`가 빔 | 400 |
| `relation=mine`이고 `assigneePropertyId`가 빔 | 통과 |
| 사람 쪽 조건이 하나도 없음 | 400 (기존) |
| `tierIds`가 팀의 묶음에 없음 | **통과** — 저장 시점이 다르다. 아무에게도 안 걸리고 화면이 깨진 규칙으로 표시한다 |

| 입력 | 결과 |

| 고칠 권한이 없음 | 403 |
| `name`이 빔 | 400 |
| `dutyIds`에 마스터에 없는 직책 ID | 통과 |

### 테스트

| # | 상황 | 기대 |
|---|---|---|

| 5-2 | 팀 관리자가 묶음을 고친다 | 200 |

## 6. 매트릭스 화면

| 약속 | 확인 방법 |
|---|---|
| 표는 행=카드 유형, 열=직책 묶음이다 | 요구사항 이미지와 자리가 같다 |
| 칸을 고치면 `source=matrix` 줄만 바뀐다 | 손으로 만든 줄이 남아 있다 |
| 표에서 저장해도 `source`가 빈 줄은 안 지운다 | FR-021 |
| 표 밖의 줄이 있으면 표가 알려준다 | FR-021 |
| 카드 유형이 정해지지 않은 보드는 표가 안 나온다 | FR-022 |
| 어느 묶음에도 없는 직책을 목록으로 보여준다 | FR-023 |
| 없는 묶음을 가리키는 규칙을 깨진 규칙으로 표시한다 | FR-024 |
| 묶음은 고칠 권한이 없어도 보인다 | FR-011c — `C-Level`이 누구인지 모르면 규칙을 못 짠다 |
| 묶음 옆에 "이 팀의 모든 보드에 적용됩니다"가 있다 | FR-011a — 영향 범위를 먼저 말한다 |
| 팀에 묶음이 없는 채로 권한을 켜면 "묶음부터 정하세요"가 뜬다 | 규칙만 깔리면 아무도 아무것도 못 본다 |

**기존 UI 패턴을 쓴다** (원칙 II). 드롭다운은 `MenuWrapper` + `Menu.Text`,
깨진 규칙 표시는 `PropertyAccessRow__broken`을 그대로 쓴다. 새 SCSS 파일을 만들지 않고
`propertyAccessSection.scss`에 블록을 더한다.

## 7. 안 바뀌는 것

| | |
|---|---|
| 관리자 통과 | 그대로 |
| 작성자 바닥 | 그대로 (게이트 안쪽 배치 포함) |
| 보드 전체보기 바닥 | 그대로 |
| 규칙이 관리 권한을 못 주는 것 | 그대로 |
| 웹소켓 수신자 거르기 | 판정만 새 순서를 쓴다 |
| 새 카드의 기본값 채우기 | `DefaultConditionValues`는 절대값 규칙에서만 나온다. 관계 규칙은 카드가 있어야 판정되므로 만들기 전에는 쓸 수 없다 |

마지막 줄이 중요하다. **관계 규칙만 있는 보드는 새 카드에 유형 기본값이 안 채워진다.**
008이 그 자리를 이미 채우고 있으므로(OKR 사다리가 깊이로 유형을 정한다) OKR 보드에서는
문제가 없다. 그 외 보드에서는 빈 값으로 시작한다 — 지금도 규칙이 값을 하나로 좁히지
못하면 그렇다.
