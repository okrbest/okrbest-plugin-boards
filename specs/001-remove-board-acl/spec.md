# Feature Specification: 보드 접근 권한(ACL) 및 소유자 개념 제거

**Feature Branch**: `001-remove-board-acl`

**Created**: 2026-07-31

**Status**: Draft

**Input**: User description: "보드 접근 권한(ACL) 추가 및 관련 로직 전체를 제거하려고 한다"

`feat/permission` 브랜치가 도입한 부서·직위 기반 보드 접근 제어(ACL)와, 같은 브랜치에서 함께 들어온 보드 소유자 개념을 걷어낸다. 보드 권한 판정을 포크 이전(`main`)의 멤버 역할 기반으로 되돌리되, 브랜치가 도입한 권한 요약 응답 구조는 유지한다.

설계 배경과 파일 단위 제거 목록은 brainstorming 산출물 `docs/superpowers/specs/2026-07-31-acl-removal-design.md`에 있다(추적 대상 아님).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 보드 관리자가 보드를 삭제할 수 있다 (Priority: P1)

지금 보드를 삭제할 수 있는 사람은 보드 소유자 한 명뿐이다. 소유자는 보드 생성자로 자동 결정되고, 소유권 이전은 현재 소유자 본인만 실행할 수 있다. 그래서 생성자가 퇴사하거나 계정이 비활성화되면 그 보드는 누구도 삭제할 수 없고 관리자가 개입할 경로도 없다.

이 이야기는 보드 관리자와 팀·시스템 관리자가 다시 보드를 삭제할 수 있게 만든다.

**Why this priority**: 사용자에게 드러나는 유일한 기능 회복이자 현재 운영에서 실제로 막힌 지점이다. 나머지 제거 작업은 이 변경 없이도 기술적으로 성립하지만, 이것 하나만으로도 독립적인 가치가 있다.

**Independent Test**: 보드를 만들지 않은 보드 관리자 계정으로 보드 삭제를 시도해 성공하는지 확인한다. 팀 관리자 계정으로도 같은 시도를 반복한다.

**Acceptance Scenarios**:

1. **Given** 사용자 A가 만든 보드에 사용자 B가 관리자 역할로 참여한 상태, **When** 사용자 B가 보드 삭제를 요청하면, **Then** 보드가 삭제된다
2. **Given** 보드에 편집자 역할로 참여한 사용자, **When** 그 사용자가 보드 삭제를 요청하면, **Then** 권한 없음으로 거부된다
3. **Given** 보드 생성자 계정이 비활성화된 보드, **When** 다른 보드 관리자가 삭제를 요청하면, **Then** 보드가 삭제된다
4. **Given** 보드에 참여 중인 팀 관리자, **When** 삭제를 요청하면, **Then** 보드가 삭제된다

---

### User Story 2 - 보드 공유 화면이 멤버 관리에만 집중된다 (Priority: P2)

보드 공유 화면에 부서·직위 단위 권한을 등록하는 "보드 접근 권한(ACL)" 섹션과 소유권 이전 영역이 있다. 두 기능이 사라지면 화면에는 사람 단위 멤버 초대·역할 조정·링크 공유만 남는다.

**Why this priority**: 사용자가 직접 보는 변화이지만 기능 상실이지 회복이 아니다. P1 없이 단독으로 배포해도 화면은 정상 동작한다.

**Independent Test**: 보드 관리자로 공유 화면을 열어 ACL 섹션과 소유권 이전 영역이 보이지 않고, 멤버 초대·역할 변경·링크 공유가 정상 동작하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 보드 관리자가 공유 화면을 연 상태, **When** 화면을 확인하면, **Then** 부서·직위 권한 등록 영역이 존재하지 않는다
2. **Given** 보드 관리자가 공유 화면을 연 상태, **When** 화면을 확인하면, **Then** 소유권 이전 영역이 존재하지 않는다
3. **Given** 보드 관리자가 공유 화면을 연 상태, **When** 멤버를 초대하고 역할을 바꾸면, **Then** 기존과 동일하게 반영된다
4. **Given** 이전에 소유자로 표시되던 멤버, **When** 멤버 목록을 확인하면, **Then** 다른 멤버와 동일하게 역할 변경 메뉴가 노출된다

---

### User Story 3 - 접근 범위 축소를 배포 전에 파악할 수 있다 (Priority: P3)

부서·직위 ACL이나 전체공개 직위로만 접근하던 사용자는 이 변경 이후 해당 보드에 접근할 수 없다. 운영자는 배포 전에 영향을 받는 보드와 사용자를 파악해야 한다.

**Why this priority**: 코드 변경이 아니라 배포 운영 절차다. 기능 자체는 P1·P2로 완성되지만, 이 확인 없이 배포하면 사용자가 예고 없이 접근을 잃는다.

**Independent Test**: 배포 전 조회로 접근 권한 항목이 등록된 보드 목록과 전체공개 직위 보유자 명단을 산출할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 배포 전 시점, **When** 운영자가 영향 범위를 조회하면, **Then** 접근 권한 항목이 등록된 보드 수와 식별자를 확인할 수 있다
2. **Given** 영향받는 보드가 식별된 상태, **When** 운영자가 조치를 결정하면, **Then** 해당 사용자를 보드 멤버로 직접 추가하거나 접근 상실을 공지할 수 있다

---

### Edge Cases

- **부서·직위 접근 권한으로만 접근하던 사용자**: 해당 보드가 목록·검색에서 사라지고 직접 접근도 차단된다. 멤버십이나 공개 보드 규칙으로 도달할 경로가 없으면 완전히 접근을 잃는다
- **전체공개(CEO/임원) 직위 보유자**: 팀의 모든 보드를 보던 상태에서 일반 사용자와 동일한 범위로 축소된다
- **소유권 이전을 실행한 적 있는 보드**: 저장된 소유자 정보가 무시된다. 삭제 권한은 멤버 역할로만 판정된다
- **배포 시점에 접근 권한 화면을 열어둔 사용자**: 저장을 시도하면 해당 요청 경로가 사라져 실패한다. 화면 새로고침으로 해소된다
- **보드 생성자 계정이 비활성화된 보드**: 기존에는 삭제 불가였으나 이제 보드 관리자가 삭제할 수 있다
- **부서·직위 마스터 데이터**: 외부에서 관리되는 원본은 그대로 남고 보드 권한 판정에서만 참조가 끊긴다

## Requirements *(mandatory)*

### Functional Requirements

**제거**

- **FR-001**: 시스템은 부서·직위·부서+직위 단위의 보드 접근 권한 항목을 저장·조회·평가하지 않아야 한다
- **FR-002**: 시스템은 보드 접근 권한 항목을 등록·수정·삭제하는 외부 인터페이스를 제공하지 않아야 한다
- **FR-003**: 시스템은 부서 목록·직위 목록을 조회하는 외부 인터페이스를 제공하지 않아야 한다
- **FR-004**: 시스템은 전체공개 직위 보유자에게 팀의 모든 보드를 노출하는 규칙을 적용하지 않아야 한다
- **FR-005**: 시스템은 보드 목록·검색 결과를 접근 권한 항목이나 직위로 확장하지 않아야 한다. 결과는 멤버십과 공개 보드 규칙으로만 결정된다
- **FR-006**: 시스템은 보드 소유자 개념을 사용하지 않아야 한다 — 소유자 지정·조회·이전 기능을 모두 제거한다
- **FR-007**: 시스템은 권한 진단용 응답 헤더를 내보내지 않아야 한다
- **FR-008**: 보드 공유 화면은 접근 권한 등록 영역과 소유권 이전 영역을 표시하지 않아야 한다

**동작 복구**

- **FR-009**: 보드 관리자 역할을 가진 사용자는 보드를 생성하지 않았더라도 보드를 삭제할 수 있어야 한다
- **FR-010**: 팀 관리자·시스템 관리자 권한을 가진 사용자는 보드를 삭제할 수 있어야 한다
- **FR-011**: 편집자·댓글 작성자·열람자 역할만 가진 사용자는 보드를 삭제할 수 없어야 한다
- **FR-012**: 보드 멤버를 제거하거나 역할을 바꾸는 동작에 소유자 예외를 두지 않아야 한다

**데이터**

- **FR-013**: 시스템은 접근 권한 판정에 사용하던 보드 플래그 컬럼과 관련 인덱스를 데이터베이스에서 제거해야 한다
- **FR-014**: 시스템은 보드 속성에 이미 저장된 접근 권한 항목·관리자 목록·소유자 식별자를 삭제하지 않고 그대로 둔다. 읽는 경로가 사라지므로 동작에 영향을 주지 않는다

**유지**

- **FR-015**: 시스템은 사용자별 보드 권한 요약(열람·댓글·카드 편집·보드 관리·보드 삭제 가능 여부)을 조회하는 기능을 유지해야 한다
- **FR-016**: 공개 보드의 최소 역할 규칙과 명시적 멤버 역할에 따른 권한 판정을 유지해야 한다

**규정 준수**

- **FR-017**: 이번 변경에서 추가하는 스키마 변경의 되돌리기 정의는 constitution 원칙 VII의 규약을 따라야 한다
- **FR-018**: 접근 권한 플래그를 도입했던 기존 스키마 변경의 되돌리기 정의가 같은 규약을 위반하고 있으므로 함께 바로잡아야 한다

### Key Entities

- **보드 접근 권한 항목**: 부서·직위·부서+직위 조합에 부여된 보드 권한 수준. 보드 속성 안에 목록으로 저장된다. 제거 대상
- **부서·직위 마스터**: 팀 단위로 관리되는 조직 단위·직위 목록. 접근 권한 항목의 대상 선택지로만 쓰였다. 참조 제거 대상
- **보드 소유자**: 보드 삭제 권한을 단독으로 가지던 사용자. 명시 지정이 없으면 생성자로 폴백했다. 제거 대상
- **보드 권한 요약**: 사용자가 특정 보드에서 무엇을 할 수 있는지 나타내는 응답. 유지 대상이며 산출 근거에서 접근 권한 항목과 소유자만 빠진다
- **보드 멤버 역할**: 관리자·편집자·댓글 작성자·열람자. 변경 후 권한 판정의 유일한 근거

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 보드를 생성하지 않은 보드 관리자의 보드 삭제 성공률이 100%다
- **SC-002**: 생성자 계정 비활성화로 삭제 불가 상태였던 보드가 0건이 된다 — 관리자가 모두 삭제할 수 있다
- **SC-003**: 편집자 이하 역할 사용자의 보드 삭제 시도는 100% 거부된다
- **SC-004**: 보드 공유 화면에서 접근 권한 등록·소유권 이전 관련 조작 경로가 0개다
- **SC-005**: 변경 전후 자동화 검증 결과를 비교했을 때 새로 발생한 실패가 0건이다. 접근 권한 기능 자체를 검증하던 항목의 감소는 정상으로 본다
- **SC-006**: 접근 권한·소유자 기능의 잔여 참조가 0건이다 — 기능이 부분적으로 남아 예측 불가능하게 동작하는 상태가 없다
- **SC-007**: 되돌리기 정의 규약 검사가 전체 스키마 변경에서 통과한다
- **SC-008**: 보드 목록 조회와 검색에서 팀 전체 보드를 훑는 후보 조회가 발생하지 않는다 — 결과 범위가 멤버십과 공개 보드 규칙으로 한정되므로 조회량이 사용자가 실제로 접근 가능한 보드 수를 넘지 않는다

## Assumptions

- **접근 권한 항목과 소유자 식별자는 이 브랜치가 처음 도입했다.** `main`에는 두 개념이 모두 없다. 따라서 제거는 신규 기능 철회이지 기존 동작 변경이 아니다
- **보드 삭제 권한의 기준은 `main`의 판정으로 되돌린다.** 보드 관리자 역할 보유자와 팀·시스템 관리자가 삭제할 수 있다
- **보드 속성에 남는 데이터는 방치한다.** 세 항목 모두 기존 속성 맵에 추가된 키이며 스키마 변경이 아니다. 정리 작업은 데이터베이스 종류별로 갈라져 위험 대비 이득이 적다
- **접근 권한 판정용 플래그 컬럼은 이미 실환경에 반영되었다.** 따라서 기존 마이그레이션을 수정하지 않고 상위 번호 마이그레이션으로 걷어낸다
- **부서·직위 마스터 원본은 이 저장소가 관리하지 않는다.** 참조만 끊으며 원본 데이터는 건드리지 않는다
- **권한 요약 응답 구조는 유지한다.** 화면이 이미 이 구조로 권한을 판정하므로 산출 근거만 바꾼다
- **팀 관리자의 보드 멤버십 요구 조건은 이번 범위 밖이다.** `main`은 팀 관리자에게 보드 멤버십 없이도 권한을 주지만 현재 브랜치는 명시적 멤버십을 요구한다. 이 차이는 삭제뿐 아니라 모든 권한에 걸치므로 별도 과제로 둔다. 다만 검증 단계에서 실제 동작을 기록한다

## Dependencies

- 데이터베이스 마이그레이션 실행 권한 (플래그 컬럼·인덱스 제거)
- 되돌리기 스크립트 규약을 자동 집행하는 지속적 통합
- 인터페이스 변경에 따른 목 객체 재생성

## Out of Scope

- 사용자별 보드 권한 요약 기능의 제거
- 팀 관리자에게 보드 멤버십 없이 권한을 부여하는 `main` 동작의 복원
- 이 브랜치에 이미 존재하는 접근 권한 무관 결함 — 권한 처리부의 상태 접근 방어 부재, 스냅샷 미갱신, 테스트 도구 버전 비호환, 특정 라이브러리 변환 설정 누락
- 보드 속성에 남은 접근 권한·소유자 데이터의 정리
- 부서·직위 마스터 데이터 자체의 폐기
