# Phase 0 연구: 조직 속성 값에 색을 입힌다

**Feature**: `007-org-property-colors`

명세에 `[NEEDS CLARIFICATION]`이 없다. 저장 범위와 기본색은 명세를 쓰기 전에 정했다.
그래서 이 문서가 푸는 것은 **어떻게 만들 것인가**다.

---

## R1. 색을 어디에 저장하나

**결정**: `board.properties`에 새 키 하나(`orgColors`)를 만들고 `{조직 단위 ID: 색 키}`
맵을 넣는다. 사용자가 고른 색만 들어간다.

**근거**: 접근 규칙(`propertyAccess`)이 이미 이 자리에 이 방식으로 산다. 읽기는
`board.properties?.[KEY]`, 쓰기는 보드를 복제해 키를 갈아 끼우고 `mutator.updateBoard`.
같은 경로를 쓰면 실행 취소·웹소켓·권한이 전부 공짜로 따라온다.

**절대 하면 안 되는 대안 — `cardProperties[].options`에 넣기**

가장 먼저 떠오르는 자리이고, 선택 속성이 실제로 거기에 색을 넣는다. 그런데 조직
속성은 **그 배열이 비어 있다는 사실 자체가 기능을 한다.** 접근 규칙 편집기는 선택지
목록을 가진 속성만 규칙 후보로 올린다(`propertyAccessRow.tsx`). 조직 속성이 후보에서
빠지는 건 코드가 막아서가 아니라 옵션이 비어서다.

색을 옵션 배열에 넣는 순간 본부·부서·직책이 규칙 후보 목록에 나타나고 006 FR-011이
깨진다. 규칙을 만들려 해도 `propertyValueId`가 색 항목을 가리키게 되어 뜻이 없는 규칙이
된다. **이 함정은 계약서와 quickstart 양쪽에 적어 둔다.**

**다른 대안**:

- **팀 단위 저장** — 같은 본부가 어느 보드에서나 같은 색이 된다. 팀 저장소와 API가
  새로 필요해 서버까지 번진다. 명세 단계에서 범위 밖으로 정했다.
- **조직 마스터에 색 칼럼** — 메인 서버 소유다. 이 플러그인은 읽기만 한다.

## R2. 지정하지 않은 값의 색을 어떻게 정하나

**결정**: 조직 단위 ID를 해시해 팔레트 인덱스를 뽑는다. 저장하지 않는다.

```
색 = 팔레트[hash(unitId) % 팔레트크기]
```

팔레트는 `Constants.menuColors`에서 `propColorDefault`를 뺀 **9종**이다.

**근거**: 세 가지가 공짜로 따라온다.

- **저장이 없다** — 마이그레이션도, 빈 보드의 초기화도, 조직이 늘 때의 뒷정리도 없다.
- **어디서나 같다** — 같은 본부는 다른 보드, 다른 계정, 다른 기기에서 같은 색이다.
  저장했다면 보드마다 달라졌을 것이다.
- **처음부터 칠해져 있다** — 사용자가 아무것도 하지 않아도 값이 구분된다. 조직이 수십
  개인 보드에서 하나씩 고르라고 하면 아무도 안 하므로, 이쪽이 기본이어야 한다.

회색을 빼는 이유는 대비다. `propColorDefault`가 섞이면 "자동 배정된 값"과 "색이 없는
값"이 같아 보인다.

**해시는 안정적이어야 한다.** 배포마다 색이 바뀌면 사용자는 버그로 읽는다. 자바스크립트
내장 해시가 없으므로 짧은 문자열 해시(djb2 계열)를 직접 쓴다 — 몇 줄이고, 결과가
플랫폼·버전에 의존하지 않는다.

**대안**:

- **순서 기반 배정**(마스터 목록의 n번째 → n번째 색) — 조직 하나가 추가되거나 이름이
  바뀌어 정렬이 밀리면 **모든 색이 한 칸씩 밀린다.** ID 해시는 그 조직 단위에만 묶인다.
- **전부 회색 유지, 지정한 것만 칠하기** — 명세 단계에서 사용자가 자동 배정을 골랐다.
- **색을 처음 볼 때 랜덤으로 정해 저장** — 저장이 생기고, 같은 조직이 보드마다 달라지고,
  누가 먼저 열었느냐에 색이 달린다. 재현되지 않는 상태를 만든다.

## R3. 색 결정 규칙을 어디에 두나

**결정**: 006이 만든 `properties/orgLabels.ts`에 얹는다. 이름을 푸는 함수 옆에 색을
푸는 함수를 둔다.

**근거**: 006에서 "조직 값의 이름을 푸는 곳"을 하나로 모았고, 소비자가 셋이다 — 카드
에디터, 필터, 그룹 헤더. **색의 소비자도 정확히 같은 셋이다.** 이름과 색은 "이 ID를
사람이 보는 무엇으로 바꾸나"라는 한 질문의 두 면이라, 다른 파일에 두면 세 소비자가
두 곳을 import하게 된다.

우선순위도 여기서 한 번만 정한다.

```
마스터에 없는 값 → 경고색   (지정 색이 있어도 이긴다)
지정한 색이 있음  → 그 색
그 외             → 해시 색
```

**대안**: 색 전용 모듈을 새로 만든다. 파일이 하나 늘고 import가 둘로 갈린다. 얻는 게
없다.

## R4. 색 고르는 UI를 어떻게 여나

**결정**: `ValueSelector`의 `fixedOptions`가 지금은 옵션 메뉴를 통째로 없애는데, 이를
**"색만 있는 메뉴"**로 바꾼다. 색 변경 핸들러가 넘어온 경우에만 메뉴를 띄운다.

**근거**: 지금 한 덩어리로 묶인 것이 사실은 성격이 다르다.

| 항목 | 조직 속성에서 |
|---|---|
| 이름 변경·삭제·추가 | **불가능해야 한다** — 마스터는 메인 서버 소유다 |
| 색 변경 | 가능해야 한다 — 색은 보드의 표시 설정이지 조직 데이터가 아니다 |

메뉴에는 이미 `onStartRename`이 있을 때만 이름 변경을 그리는 패턴이 있다. 색도 같은
결로 `onChangeColor` 유무에 매단다. 새 위젯을 만들지 않고 기존 `Menu.Color`를 그대로
쓰므로 선택 속성과 조작이 같다(원칙 II).

**대안**:

- **새 prop `allowColorOnly` 추가** — 상태가 둘(`fixedOptions`, `allowColorOnly`)로 늘어
  조합이 넷이 되는데 의미 있는 건 셋이다. 핸들러 유무로 판단하면 조합이 생기지 않는다.
- **속성 메뉴(속성 이름 옆)에서 색을 관리** — 값이 아니라 속성 단위 화면이라 "이 본부의
  색"을 고르는 자리로는 멀다. 선택 속성이 값 옆에서 고르는 것과도 어긋난다.

## R5. 그룹 헤더 색을 어디서 채우나

**결정**: `centerPanel`에서 이름을 덮어쓰는 그 자리에 색도 함께 채운다. `boardUtils`는
건드리지 않는다.

**근거**: `boardUtils`의 그룹 생성은 모든 속성 유형이 지나는 공용 경로다. 조직 전용
조회를 여기 넣으면 선택·사람·날짜 그룹까지 조직 마스터를 훑는다. 006에서 조직 그룹의
**이름**을 `centerPanel`이 덮어쓰기로 한 것과 같은 이유다 — 조직에만 필요한 정보는
조직만 아는 자리에서 채운다.

**대안**: `boardUtils`에 조직 분기를 넣는다. 공용 경로가 특정 속성 유형을 알게 되고,
스토어에 닿지 않는 순수 함수였던 성질도 깨진다.

---

## R6. 필터 목록은 왜 지금 색이 없나

**결정**: 조직 필터 항목을 `<span>`에서 `Label` 위젯으로 바꾼다.

**근거**: 다른 필터 패널(선택 속성)은 이미 `Label`로 그려 옵션 색이 보인다. 조직 필터만
텍스트라 색을 넣을 자리가 없다. 위젯을 바꾸면 세 자리의 모양이 같아진다(FR-007).

**주의**: 체크박스 정렬과 검색 강조가 `Label`로 바뀌며 어긋날 수 있다. 새 SCSS 파일을
만들지 말고 기존 필터 패널 스타일 안에서 맞춘다(원칙 II).
