# 검증 가이드: 조직 속성 값에 색을 입힌다

**Feature**: `007-org-property-colors` | **Date**: 2026-08-14

구현이 실제로 동작하는지 종단으로 확인하는 절차다. 요구사항 식별자는
[spec.md](./spec.md), 판정 규칙은 [data-model.md](./data-model.md)에 있다.

---

## 사전 준비

**소스만 고쳐서는 반영되지 않는다.**

```bash
cd webapp && MM_DEBUG=1 npm run debug:watch    # 저장할 때마다 자동 배포
```

배포 후 **브라우저 하드 리프레시**가 필요하다. webapp만 바꾸므로 Go 빌드는 필요 없다.

### 검증 데이터

`kkv` 팀 조직 마스터. 자동 색이 겹치는지 보려면 팔레트(9종)보다 많아야 한다.

| 종류 | 개수 |
|---|---|
| 본부 | 7 |
| 부서 | 13 |
| 직책 | 9 |

검증용 보드를 새로 만든다. 기존 OKR 보드에서 하지 않는다.

---

## 1. 색을 고르지 않아도 구분된다 (P1)

FR-001, FR-002

1. 새 보드에 본부 속성을 만들고 카드를 연다. 값 목록을 연다.
   - **확인**: 목록의 본부 7개가 **서로 다른 색**이다. 전부 회색이 아니다.
   - **확인**: 회색(Default)으로 칠해진 항목이 없다.
2. 카드에 본부 두 개를 고른다.
   - **확인**: 두 라벨의 색이 다르다.
3. 브라우저를 하드 리프레시한다.
   - **확인**: 색이 그대로다. (FR-002)
4. 같은 본부를 쓰는 **다른 보드**를 새로 만들어 같은 값을 고른다.
   - **확인**: 1번에서 본 색과 같다. 자동 색은 보드에 매이지 않는다.
5. 직책·부서 속성으로도 1~2를 반복한다.
   - **확인**: 조직 종류가 달라도 규칙이 같다.

`orgColors` 키가 아직 저장되지 않았는지 확인한다 — 자동 색은 계산이지 저장이 아니다.

```bash
docker exec -e PGPASSWORD='...' mattermost-postgres psql -U mmuser -d mattermost_test -A -t -c \
  "SELECT properties->'orgColors' FROM focalboard_boards WHERE id='<검증 보드 ID>';"
# 기대: 빈 결과 (키 없음)
```

## 2. 색을 직접 고른다 (P2)

FR-003, FR-004, FR-005, FR-006, FR-010

1. 값 목록에서 본부 하나의 메뉴를 연다.
   - **확인**: 팔레트가 나온다.
   - **확인**: **이름 변경·삭제·추가가 없다.** (FR-010)
2. 파랑을 고른다.
   - **확인**: 그 값이 나오는 자리가 전부 파랑으로 바뀐다.
   - **확인**: 다른 본부의 색은 그대로다.
3. 저장을 확인한다.
   ```bash
   # 기대: {"<본부 ID>": "propColorBlue"}
   docker exec ... -c "SELECT properties->'orgColors' FROM focalboard_boards WHERE id='<보드 ID>';"
   ```
   - **확인**: `cardProperties`의 그 속성 `options`는 **여전히 빈 배열**이다. 색이 옵션에 들어가면 안 된다.
4. 색 지정을 해제한다.
   - **확인**: 회색이 아니라 **1절에서 본 자동 색**으로 돌아간다. (FR-005)
   - **확인**: 저장에서 그 키가 사라진다.
5. 실행 취소(Ctrl+Z)를 눌러 본다.
   - **확인**: 색이 이전 상태로 돌아간다.
6. **다른 보드**를 열어 같은 본부를 본다.
   - **확인**: 그 보드의 색은 바뀌지 않았다. (FR-006)

---

## 3. 거를 때도 묶을 때도 같은 색 (P3)

FR-007

1. 2절에서 색을 지정한 보드에서 필터를 열고 그 조직 속성을 고른다.
   - **확인**: 값 목록의 색이 카드에서 본 색과 같다.
2. 같은 속성으로 묶는다.
   - **확인**: 그룹 제목의 색이 카드에서 본 색과 같다.
   - **확인**: 값이 여럿인 그룹은 첫 값의 색이다.
3. 색을 하나 더 바꾼다.
   - **확인**: 카드·필터·그룹 **세 자리가 동시에** 바뀐다.

---

## 4. 사라진 값은 경고색이 이긴다 (FR-009)

1. 카드에 직책 하나를 넣고 그 직책의 색을 파랑으로 지정한다.
2. 조직 관리에서 그 직책을 비활성으로 바꾼다.
3. 새로고침한다.
   - **확인**: 파랑이 아니라 **경고색 + `(removed)`** 다.
   - **확인**: 그룹 헤더와 내보내기도 사라진 값 처리 그대로다.
4. 직책을 다시 활성으로 되돌린다.
   - **확인**: 지정한 파랑이 다시 보인다. 지정은 지워지지 않았다.

---

## 5. 접근 규칙이 그대로인지 (FR-011) — 가장 중요한 회귀

색 저장이 접근 규칙을 오염시키지 않았는지 본다.

1. 색을 지정하기 **전에** 공유 대화상자를 열어 규칙의 속성 후보 목록을 적어 둔다.
2. 색을 여러 개 지정한다.
3. 다시 규칙의 속성 후보 목록을 연다.
   - **확인**: 목록이 **1번과 똑같다.**
   - **확인**: 본부·부서·직책이 후보에 **없다.**

여기서 조직 속성이 나타나면 색을 `options` 배열에 넣은 것이다
([research.md](./research.md) R1).

## 6. 담당자는 그대로 (FR-012)

1. 담당자·다중 사용자 속성이 있는 카드를 연다.
   - **확인**: 아바타와 이름이 예전 그대로다. 배경색이 생기지 않았다.

## 7. 회귀 확인

005·006 동작이 그대로인지 본다. SC-006.

1. 본부를 고르면 부서 목록이 좁혀진다.
2. 본부를 바꾸면 맞지 않는 부서 값이 정리된다.
3. 담당자 후보가 조직으로 좁혀진다.
4. 직책 목록은 좁혀지지 않는다.
5. CSV 내보내기에 이름이 나온다.

## 8. 품질 게이트

webapp만 닿는다. Go 파일을 안 바꿨는지 먼저 확인한다(`git diff --stat`).

```bash
make webapp-ci
```

기준선에서도 실패하므로 **개수가 아니라 실패 목록 diff로 판정한다.** 세 단계를 따로
돌려 대조한다.

```bash
cd webapp
npm run check          # eslint + stylelint
npm run test           # Jest
npm run check-types    # tsc
```

기준선은 `main`에서 같은 명령을 돌려 얻는다.
